## 배경 개념: 부품 질문에 답하려면 부품 자료가 있어야 한다

전자회로를 설계하는 AI는 "이 부품의 핀이 몇 번이고 이름이 뭔가"를 **지어내지 않고** 알아야 합니다. 모델에게 맡기면 그럴듯한 틀린 표가 나옵니다. 그래서 공개된 부품 라이브러리를 읽어 **카탈로그**로 만들고, 핀 질문에는 모델이 아니라 이 카탈로그의 값으로 답하게 했습니다.

이 장은 부품 자료를 확보한 과정을 **라이선스 확인 → 변환 → 연결 점검 → 다른 자료와 교차 검증 → 질문에 연결**의 순서로 기록합니다. 두 번 있었던 "내 코드가 특정 형식에만 맞춰져 있었다"는 결함도 함께 적습니다.

```text
공개 부품 라이브러리 (파일)
   ├─ KiCad 공식 라이브러리   심볼 223개 파일 → 부품 22,911개
   └─ LibrePCB 라이브러리      저장소 48개   → 장치 1,866개
              ↓ 읽기 전용 변환 (원본은 바꾸지 않음)
부품 카탈로그 (핀 번호·이름·전기 유형, 설명, 데이터시트 링크)
              ↓ 연결 점검 (풋프린트·참조가 실제로 있는가)
              ↓
채팅: "NE555 핀 번호" → 모델을 거치지 않고 카탈로그 값으로 답
```

| 파일 | 역할 |
|---|---|
| `kicad_parts.py` | KiCad 심볼 파일 읽기, 카탈로그 검색, 핀 질문 응답, LibrePCB 추가분 이어 붙이기 |
| `scripts/build-kicad-catalog.py` · `scripts/build-kicad-library.py` | KiCad 카탈로그와 풋프린트 목록 만들기 |
| `librepcb_parts.py` | LibrePCB 라이브러리 읽기 (장치·컴포넌트·패키지·분류를 uuid로 연결) |
| `scripts/build-librepcb-catalog.py` | LibrePCB 카탈로그·출처·연결 점검 결과 만들기 |
| `tests/test_kicad_parts.py` · `tests/test_librepcb_parts.py` | 서버·네트워크 없이 도는 단위 테스트 |

만든 자료는 모두 `data/` 아래에 두며 GitHub에 올라가지 않습니다. KiCad 공식 라이브러리는 CC-BY-SA 4.0(설계에 쓰는 것은 자유, 라이브러리를 모음으로 재배포하면 같은 라이선스)이어서 파생 모음을 저장소에 올리지 않습니다.

## 라이선스부터 확인한다

부품 자료를 모으기 전에 **가져다 써도 되는지**를 원문으로 확인했습니다.

| 자료 | 라이선스 확인 | 사용 방식 |
|---|---|---|
| KiCad 공식 라이브러리 | CC-BY-SA 4.0 + 예외 (웹 확인) | 이 PC에서 읽어 카탈로그 생성. 파생 모음은 저장소에 올리지 않음 |
| LibrePCB 라이브러리 (GitHub 조직, 저장소 48개) | 저장소마다 GitHub의 라이선스 표시가 CC0-1.0, **내려받은 48개 모두 `LICENSE.txt`에 CC0 1.0 Universal 전문이 있는 것을 확인** | 이 PC의 `data/` 안에서만 사용, 출처·커밋 번호를 기록 |
| easyeda2kicad (변환 도구) | AGPL-3.0 (설치한 1.0.1) | 우리 코드에 `import`하지 않고 **외부 프로그램으로만 실행** |
| Horizon 풀 · SparkFun · SnapMagic 등 | 일부는 미확인이거나 대량 공유 금지 약관 | 사용하지 않음 |

저장소의 라이선스 표시를 믿기만 하지 않고, 내려받은 48개 저장소의 `LICENSE.txt`를 열어 CC0 문구가 실제로 있는지 검사했습니다. 이 검사 결과는 출처 파일(`SOURCE.json`)에 저장소별 커밋 번호와 함께 남습니다.

## LibrePCB 라이브러리

KiCad에 없는 부품(메이커 보드·모듈, 센서)을 보완하려고 LibrePCB 라이브러리를 내려받았습니다. 얕은 복제(`git clone --depth 1`)로 저장소 48개를 받았고(.git 포함 약 290MB), 기존 KiCad 카탈로그는 건드리지 않고 `data/library_staging/librepcb/`에 따로 두었습니다.

**구조** — 한 부품이 파일 여러 개에 나뉘어 있고, 서로 uuid로 가리킵니다.

```text
dev/<uuid>/device.lp         장치: 이름·설명·키워드·분류·데이터시트 링크·제조사 부품 번호,
                             component(컴포넌트 uuid), package(패키지 uuid), pad(패드 uuid → 신호 uuid)
cmp/<uuid>/component.lp      컴포넌트: 신호(uuid · 이름 · 전기 역할)
pkg/<uuid>/package.lp        패키지: 패드(uuid · 이름 = 핀 번호)
cmpcat/<uuid>/component_category.lp   분류 (이름 · 부모 uuid)
```

핀 하나를 알려면 **장치의 패드 → 패키지의 패드 이름 + 컴포넌트의 신호**(패드 이름 = 핀 번호, 신호 = 핀 이름·역할)를 이어야 합니다. 그리고 장치가 **다른 라이브러리**의 컴포넌트·패키지를 참조할 수 있어서, 48개를 모두 합쳐 uuid로 찾습니다.

**파일** `librepcb_parts.py` · 원본 발췌

```python
def build(self) -> tuple[list[dict], dict]:
    """장치마다 부품 항목을 만든다. 돌려주는 값: (항목 목록, 연결 점검 결과)."""
    ...
    for item in self.devices:
        node, lib = item["node"], item["library"]
        comp = self.components.get(_first_atom(node, "component"))
        pkg = self.packages.get(_first_atom(node, "package"))
        ...
        for pad in _children(node, "pad"):
            pad_name = (pkg or {}).get("pads", {}).get(pad[1])
            sig_uid = _first_atom(pad, "signal")
            if sig_uid == NO_SIGNAL:
                sig_uid = ""                           # (signal none): 이 패드는 연결 없음으로 명시된 것이다
            signal = (comp or {}).get("signals", {}).get(sig_uid) if sig_uid else None
            if pad_name is None or (sig_uid and signal is None):
                report["pads_unresolved"] += 1          # 참조한 패드·신호를 찾지 못함: 핀 이름 없이 표시
```

- 파일은 KiCad 파서와 **같은 S-표현식 파서**로 읽습니다. 특정 도구의 표기에 맞춘 정규식이 아닙니다. 48개 저장소의 장치·컴포넌트·패키지·심볼 파일을 읽어 **오류가 0**이었습니다.
- 번역 이름(`(name (locale "de") "...")`)은 건너뛰고 기본 이름만 씁니다. 분류는 부모를 따라 `ICs > Amplifiers` 같은 경로로 만듭니다.
- 참조를 찾지 못한 경우는 조용히 버리지 않고 **개수를 세어 보고서에 남깁니다.** 읽지 못한 파일도 목록에 남기고 나머지는 계속 읽습니다.

### 연결 점검에서 찾은 내 결함

처음 만든 변환기의 점검 결과에 `pads_unresolved 104`가 나왔습니다. "참조한 신호를 못 찾았다"는 뜻이라 파서 결함인지 자료의 결함인지부터 가렸습니다. 값을 모아 보니 104건이 **모두 `none`** 이었습니다. `(signal none)`은 LibrePCB가 "이 패드는 어떤 신호에도 연결하지 않음"을 명시하는 값인데, 제가 이것을 "못 찾은 참조"로 세고 있었습니다. 연결 없음으로 처리하도록 고친 뒤 점검 결과가 0이 됐습니다. **점검 결과가 0이 아니면 숫자를 믿기 전에 그 값이 무엇인지부터 확인합니다.**

## 핀 질문에 연결하기

`kicad_parts.parts_catalog()`가 KiCad 카탈로그에 LibrePCB 장치를 이어 붙입니다. 규칙은 두 가지입니다.

- **이름이 같은 것은 KiCad만 씁니다.** 출처가 다른 두 표를 섞으면 "핀 배치가 서로 다릅니다"라고 되묻게 되고, 공식 라이브러리를 우선하는 편이 낫습니다. 폐기된 장치와 핀이 없는 장치도 뺍니다. 결과는 978개가 더해져 **23,889개**입니다.
- **LibrePCB에서 온 답에는 경고를 반드시 붙입니다.**

```text
ESP32-DevKitC-32E 핀 정보입니다 (LibrePCB 공개 라이브러리 `LibrePCB/Espressif:ESP32-DevKitC-32E` 기준, 핀 38개).
커뮤니티가 만든 데이터이고 사람의 검증·승인 전입니다. 설계에 쓰기 전에 데이터시트로 확인해야 합니다.
```

`.env`의 `CHAT_PARTS_LIBREPCB=false`로 LibrePCB 추가분을 끌 수 있습니다. 실제 서버에서 자동 모드로 확인했습니다(2026-11-14): `ESP32-DevKitC-32E 핀 이름`은 LibrePCB 경고가 붙은 라이브러리 답으로, `NE555 핀 번호와 이름 알려줘`는 이전과 같은 KiCad 공식 표기로 나왔습니다.

**부품 이름 전체로 찾기** — 처음에는 부품 번호 낱말(문자와 숫자가 함께 있는 한 낱말)만 인식해서 `Arduino Nano V3`처럼 띄어쓰기가 있는 이름은 못 찾고 질문이 모델로 넘어갔습니다. 부품 번호 낱말로 못 찾았을 때만, 질문에 **이름 전체**가 그대로 있으면 찾도록 했습니다(영문·숫자만 남겨 비교, 숫자가 든 8자 이상 이름, 가장 긴 일치만).

| 측정 | 결과 |
|---|---|
| 이름에 띄어쓰기·밑줄이 있는 부품 3,722개를 `<이름> 핀 정보`로 질문 | 3,695개(99.3%)는 그 부품으로 답함 |
| 나머지 27개 | 번호 낱말 경로가 먼저 **이름이 다른 부품**에 답함(예: `FTDI FT232RL`을 물었는데 KiCad의 `FT232RL`). 10개는 핀 표가 같고 17개는 핀 표가 다름 |
| 문서·일반 질문 82개 뒤에 "핀 정보"를 붙였을 때 부품으로 잘못 인식 | 5개. 모두 기존 숫자 낱말 경로(`2024`·`404`처럼 숫자가 부품 이름에 들어 있는 경우)이고 이름 전체 경로에서는 0 |

**한계** — 같은 칩이어도 심볼·패키지가 다른 별개 항목이면, 번호 낱말이 먼저 다른 항목에 답할 수 있습니다. 질문에 숫자가 없는 이름(`Raspberry Pi Pico`처럼)은 이름 전체 경로에서도 인식하지 않습니다.

## 핵심 정리

- 부품의 핀은 모델이 아니라 **공개 라이브러리의 값**으로 답합니다. 모델에게 맡기면 그럴듯한 틀린 표가 나옵니다.
- 자료를 모으기 전에 라이선스를 확인하고, 내려받은 뒤에도 라이선스 파일 원문을 직접 검사합니다. 변환 도구가 AGPL이면 우리 코드에 넣지 않고 외부 프로그램으로만 씁니다.
- 파일 형식에 맞춘 정규식 대신 **형식을 가정하지 않는 파서**를 씁니다. 다른 도구의 파일을 읽히면 0개를 읽던 결함이 이렇게 드러났습니다.
- 연결 점검 결과는 **조용히 버리지 않고 세어 남깁니다.** 0이 아니면 그 값이 무엇인지부터 확인합니다(`(signal none)` 104건은 파서 결함이 아니라 내 해석의 결함이었습니다).
- 다른 자료와 교차 검증할 때 **이름이 아니라 구조**(핀 번호 집합)로 먼저 비교하고, 이름이 다르면 표기 차이인지 직접 확인합니다.
- 커뮤니티 데이터는 `proposed`로 표시하고, 답에도 "사람의 검증 전"임을 밝힙니다. 공식 라이브러리와 이름이 같으면 공식을 우선합니다.
- 전기 유형과 정격이 없다는 한계는 숨기지 않고 적습니다. 다음 단계는 데이터시트에서 정격을 확보해 사람이 승인하는 것입니다.
