## 배경 개념: 한국어로 물으면 영어 부품 자료를 어떻게 찾는가

제7장에서 만든 부품 카탈로그는 이름·설명·키워드·분류가 모두 **영어**입니다. 그런데 사용자는 "5V를 3.3V로 낮추는 레귤레이터 뭐 쓰면 돼?"처럼 **한국어**로 묻습니다. 낱말을 그대로 맞춰 보는 검색은 이런 질문에서 하나도 맞히지 못했습니다(아래 평가에서 상위 5개 적중률 0.000).

이 장은 그 간격을 메운 과정을 기록합니다. 세 층을 차례로 쌓았습니다.

```text
① 개념 뼈대      KiCad 카탈로그의 분류·키워드 → 개념 그래프 (출처: 라이브러리 버전·근거 부품 수)
② 한·영 다리      한국어 용어 → 영어 개념 (후보 사전, 위임 승인·검토) + Wikidata 근거 보조
③ 검색과 답       질문 이해 → 의미 검색(임베딩) → 코드가 카탈로그 값으로 답 작성
           + 문서 쪽 한국어 분석기(노리) 준비 — 평가 결과 기본 꺼짐
```

가장 중요한 원칙은 "**충실한 자료 = 항목마다 출처**"입니다. 출처가 없는 대응은 아무리 그럴듯해도 사람이 승인하기 전에는 사실로 다루지 않습니다.

| 파일 | 역할 |
|---|---|
| `ontology_graph.py` · `scripts/build-ontology-graph.py` | 카탈로그에서 개념 뼈대 그래프 만들기, 출처 주석 |
| `static_data/ontology_ko_en_seed.json` · `scripts/build-ontology-ko.py` | 한·영 후보 사전(전부 `proposed`)과 그래프 연결 |
| `ontology_wikidata.py` · `scripts/build-ontology-wikidata.py` | Wikidata로 한·영 대응에 근거(QID) 붙이기, 분야 확인 |
| `parts_graph.py` · `parts_chat.py` | 부품 추천 질문용 LangGraph(이해 → 검색 → 답) |
| `nori_dict.py` · `scripts/build-nori-index.py` · `static_data/nori_user_dict.txt` | 노리 사용자 사전과 노리 문서 인덱스 |

만든 그래프·대응 결과·평가 질문은 모두 `data/` 아래에 있어 GitHub에 올라가지 않습니다.

## 개념 뼈대: 카탈로그에서 자동으로

KiCad 카탈로그의 **분류**(라이브러리 이름)와 **키워드**를 개념 후보로 삼아 그래프를 만들었습니다. 같은 부품에 자주 함께 붙는 키워드는 서로 관련된 개념으로 잇습니다.

| 노드 | 출처 표시 |
|---|---|
| 그래프 전체 | KiCad 공식 라이브러리를 받은 날짜, 심볼·풋프린트 커밋, 라이선스 |
| 분류(라이브러리) 노드 | 근거 부품 수, 예시 부품 3개(데이터시트가 있는 것 먼저), 읽기 쉬운 영어 이름 후보, 대표 키워드 |
| 키워드 노드 | 근거 부품 수, 예시 부품 3개 |
| 한국어 개념 노드 | "Claude가 작성한 후보, 사람 승인 전"이라고 명시 |

예를 들어 선형 레귤레이터 분류는 근거 부품이 1,630개로 표시됩니다. 처음 만든 그래프에는 이런 출처 정보가 없었습니다. 항목이 "어디서 왔는지" 답하지 못하는 그래프는 검토할 수 없어서 나중에 보탰습니다.

## 한·영 다리: 후보 사전과 그 한계

한국어 질문을 영어 개념에 잇는 사전은 **Claude가 쓴 후보**입니다. 처음에는 모든 항목이 `proposed`(승인 전)였고, 아래의 위임 승인을 거쳤습니다. 사람이 직접 확인한 것은 아니므로 교재에는 사전의 내용을 사실로 싣지 않습니다.

후보 사전의 대응에 독립된 근거를 붙이려고 **Wikidata**(누구나 쓸 수 있는 CC0 공개 지식 사전)를 이용했습니다. 항목마다 고유 번호(QID)와 주소가 있어 출처로 남길 수 있습니다.

```bash
.venv/bin/python scripts/build-ontology-wikidata.py      # 응답은 캐시에 남아 다시 돌리면 같은 결과
```

| 방향 | 하는 일 |
|---|---|
| 한국어 → 영어 | 후보 사전의 한국어 용어를 Wikidata에서 찾아, 그 항목의 영어 이름이 후보의 영어 키워드와 겹치는지 본다 |
| 영어 → 한국어 | 부품이 많이 붙은 KiCad 키워드를 찾아, 영어 이름이 정확히 같은 항목의 한국어 이름을 가져온다 |

외부로 보내는 것은 KiCad 영어 키워드와 후보 사전의 용어뿐이며, 사용자 문서 내용은 보내지 않습니다. 공용 서비스에 부담을 주지 않도록 호출 간격을 두었고, "요청이 너무 많다"(429) 응답에는 기다렸다가 다시 시도합니다.

### 같은 낱말, 다른 분야

처음 결과에는 분야가 다른 항목이 많이 섞였습니다. 영어 `arm`이 무기로, `regulator`가 정부 기관으로, `buck`이 화폐로 대응되는 식입니다. 그래서 **분야 확인** 단계를 넣었습니다. Wikidata의 분류 사슬을 따라 올라가, 항목이 전기·전자 계열의 상위 분류 11개(전자 부품, 반도체 소자, 집적회로, 센서, 전기 커넥터, 전원 공급 장치 등) 중 하나에 닿는지 봅니다.

| 한국어 용어 검증 결과 | 개수 |
|---|---|
| 영어와 맞고 분야도 전기·전자 | 48 |
| 영어와 맞지만 분야가 다름 | 25 |
| 영어와 어긋남 | 19 |
| 나머지 | Wikidata에 없음 (대부분) |

이 거르기도 완벽하지 않습니다. 다른 분야인데 남은 것(예: 프로세서 → 레지스터 항목, 믹서 → 주방 블렌더)과, 맞는데 빠진 것(예: 블루투스·타이머)이 모두 있습니다. 그래서 Wikidata 결과는 **사람 검토의 근거 보조**로만 그래프에 표시하고, 승인을 대신하지 않습니다. 또 한 가지 배운 점은 **한국어 전문 용어는 공개 사전에 적다**는 것입니다. 결국 충실한 한국어 자료는 실제 사용 문서나 전문 용어집에서 와야 합니다.

### 위임 승인: 두 검토자가 모두 동의한 것만

사용자는 개념 승인을 두 Claude 세션에 위임했습니다. 그래서 승인 규칙을 실행 전에 정했습니다. **자동 검증의 권고가 '승인'이고, 다른 세션의 독립 검토가 'OK'이며, 틀린 용어가 없는 개념만** 승인합니다. 독립 검토자는 자동 검증 결과를 보기 전에 168개를 한 항목씩 읽고 판정했습니다.

| 단계 | 결과 |
|---|---|
| 1차 합의 | 승인 114 · 승인 전 54 |
| 2차 재판정 (위험 용어는 '추천·찾아줘' 같은 말이 있을 때만 쓰도록 코드를 바꾼 뒤, 사유가 위험 용어뿐인 것만 다시 판정) | 승인 132 · 승인 전 36 |

두 검토가 엇갈린 개념이 꽤 많았습니다. 자동 검증은 '센서'·'트랜스포머'처럼 혼자 쓰면 너무 넓거나 다른 분야와 겹치는 말, '저잡음'처럼 부품이 아니라 성질인 말을 잡지 못했습니다. 독립 검토는 '에스프레소'(ESP32 제조사 이름이 아니라 커피), '레지스터'(한국어로는 보통 CPU의 register) 같은 틀린 용어를 찾았습니다. 틀린 용어가 있는 개념은 사전을 고친 새 판에서 다시 검토합니다.

승인 기록은 시드와 따로 `data/ontology/approvals.jsonl`에 남기고, 승인자를 "위임"으로 적어 사람의 직접 승인과 구분합니다. 근거 파일의 해시도 함께 남깁니다. 사용자는 `/ontology` 화면에서 개념마다 근거와 두 검토 의견을 보고 승인·보류·반려를 눌러 위임 결정을 뒤집을 수 있습니다. 승인된 개념만 쓰면 부품 질문을 받는 비율이 한 세트에서 기준보다 크게 떨어져서, 이 장을 쓰는 시점에는 승인 전 개념도 함께 쓰는 시험 설정을 유지했습니다.

## 의미 검색과 문답 그래프

부품 추천 질문은 LangGraph로 만든 작은 흐름이 처리합니다.

```text
START → classify ─(부품 추천 질문 아님)→ 기존 흐름으로
            └→ search ─(후보 없음)→ 기존 흐름으로
                  └→ answer → END
```

- **classify**: 답을 쓰는 언어 모델을 부르지 않는 규칙입니다. 사전이 아는 개념이 있고, 부품을 찾는 말(추천·후보·찾아줘 등)이 있거나 짧은 명사구(30자 이하, 물음표·'알려줘' 없음)이면 통과합니다. 사전에 정확히 없는 문구는 용어 임베딩의 유사도(문턱 0.75)로 가까운 개념에 잇습니다. 설명을 묻는 질문이나 소비자 제품 질문은 막습니다.
- **search**: 부품 22,911개의 임베딩(2,560차원)을 담은 Elasticsearch 인덱스(`kicad_parts_v2`)에서 의미가 가까운 부품을 찾습니다. Elasticsearch가 꺼져 있으면 사전의 영어 키워드로 파일 카탈로그를 찾습니다.
- **answer**: 답은 **모델이 아니라 코드가** 검색된 부품의 카탈로그 값으로 씁니다. 모델에게 맡기면 한국어가 깨지거나 없는 부품을 지어낼 수 있기 때문입니다.
- 영문 부품 이름과 "비슷한·대체"가 함께 든 질문은 그 부품의 설명·분류로 비슷한 부품을 찾습니다. 답에는 **대체 가능을 보증하지 않는다**고 적습니다.

흐름은 `/graph` 화면에서 그림으로 볼 수 있고, 질문 하나를 넣어 어느 단계를 지났는지 확인할 수 있습니다. 측정한 지연 시간(밀리초, 이 PC, 부품 질문 30개·부품이 아닌 질문 15개)은 부품 경로 전체 중앙값 45 · 상위 5% 90, 부품이 아닌 질문(첫 단계에서 끝남) 중앙값 5입니다. 답을 쓰는 언어 모델은 부르지 않고, 질문을 임베딩하는 모델만 한 번 부릅니다(중앙값 25, 위 시간에 포함).

## 평가: 자기 정답으로 채점하지 않기

처음 평가 질문은 사전을 만든 쪽이 질문과 정답을 함께 썼습니다. 정답이 자기 사전에서 나오면 점수가 좋게 나올 수밖에 없습니다(순환). 그래서 다른 세션이 **상대의 질문 파일과 개선 내용을 보지 않고** 독립 질문 세트를 썼고, 각 세트는 기준을 먼저 적은 뒤 **한 번만** 돌렸습니다. (세트 2를 쓴 쪽은 그 전에 사전의 형식을 확인하느라 첫 두 항목을 본 적이 있어, 첫 문항 하나는 영향을 받았을 수 있다고 함께 적어 두었습니다.)

정답은 KiCad 분류 이름이고, 상위 5개 결과 중 하나라도 정답 분류이면 맞힌 것으로 칩니다. 표의 값은 두 종류입니다. **검색 단독**은 모든 부품 질문을 관문 없이 의미 검색에 넣은 값이고, **처리율·오처리·처리한 질문의 적중**은 관문(classify)을 포함한 실제 흐름의 값입니다.

| 세트 | 질문 수 (부품 / 아님) | 검색 단독 상위 5개 적중 | 처리율 | 처리한 질문의 적중 | 오처리 |
|---|---|---|---|---|---|
| 세트 1 (사전을 만든 쪽이 씀, 편향 있음) | 20 / 6 | 0.95 | 0.85 | 1.000 | 0/6 |
| 세트 2 (독립) | 30 / 15 | 0.933 | 0.733 | 1.000 | 1/15 |
| 세트 3 (독립) | 25 / 20 | 0.840 | **0.560 (기준 0.60 미달)** | 0.857 | 1/20 |
| 세트 4 (독립, 약점을 요청해 섞은 세트) | 25 / 20 | 0.960 | 0.920 | 0.957 | **4/20 (기준 3 이하 미달)** |

- 처리율: 부품 질문 가운데 부품 경로가 받아 답한 비율
- 오처리: 부품이 아닌 질문을 부품 추천으로 잘못 처리한 개수
- 같은 질문에서 낱말 검색의 적중은 모든 세트에서 0.000이었습니다.

표는 **순서대로** 읽어야 합니다. 기준 미달 → 개선 → 새 세트 → 또 다른 기준 미달이 이어졌습니다. 세트 4 뒤의 오처리 수정은 독립 재검증을 거치지 않았습니다.

이 과정에서 얻은 교훈입니다.

1. 정답을 자기 사전에서 만들면 순환이 된다. 독립 질문 세트가 필요하다.
2. 이미 본 세트에서 고친 값은 일반화의 증거가 아니다. 세트 2의 처리율은 처음 열었을 때 0.733이었고, 그 세트를 보고 고친 뒤 같은 세트에서 1.00이 되었지만, 새로 받은 세트 3에서는 0.560이었다. (같은 시기의 다른 예: 데이터시트 PDF에서 핀 표를 뽑는 방법이 개발용 문서에서 0.98, 처음 보는 문서에서 0.13이 나와 과적합으로 판정하고 중단했다.)
3. 관문을 풀면 오처리가 는다. 짧은 명사구를 허용한 직후 문서 질문이 부품 경로로 새기 시작해, 다시 조였다.
4. 새 검증 세트를 매번 받으면, 고치는 쪽이 받은 약점이 세트에 스며든다. 그래서 이 방식은 세트 4로 끝냈고, 다음 검증은 **실제 사용 기록**으로 한다.

## 문서 쪽 한국어 분석기: 노리

문서 검색에는 Elasticsearch의 한국어 형태소 분석기 **노리**(analysis-nori)를 시험했습니다. 설치는 관리자 권한이 필요해 사용자가 직접 했습니다.

```bash
sudo /usr/share/elasticsearch/bin/elasticsearch-plugin install analysis-nori
sudo systemctl restart elasticsearch
```

노리 기본 사전은 조사를 떼고 합성어를 나누는 데 강하지만, 외래 전문어는 잘게 쪼갭니다.

| 문장 | 기본 노리 | 사용자 사전 적용 |
|---|---|---|
| 레귤레이터를 추천해 주세요 | 레 / 귤 / 레이터 / 추천 / 주 | 레귤레이터 / 추천 / 주 |
| 모스펫 스위칭 | 모스 / 펫 / 스위칭 | 모스펫 / 스위칭 |

### 사용자 사전: 출처 있는 용어만, 기준은 규칙으로

사전에 넣을 낱말은 후보 사전과 Wikidata(분야까지 맞은 항목의 대표 이름)에서만 고르고, 노리가 **한 글자 조각으로 깨뜨리는 낱말만** 넣었습니다. 두 글자 이상 조각으로만 나뉘면(예: 논리회로 → 논리 / 회로) 자연스러운 분해로 보고 그대로 둡니다.

처음 만든 사전(44개)은 다른 세션의 검토에서 문제가 드러났습니다. 띄어 쓴 용어를 조각으로 나누면서 일반어가 들어간 것입니다. 예를 들어 '강하'가 들어가면 '강하다'가 깨집니다. Wikidata 별칭에서는 다른 분야 말이 들어왔습니다. 규칙을 "띄어쓰기 없는 용어 전체만, 별칭은 제외"로 좁혀 22개로 줄인 뒤 평가했습니다.

### 기존 검색을 깨지 않는 설계

지금 문서 검색은 저장된 낱말 안에서 글자 조각을 찾는 방식(`*레귤레이터*`)으로 후보를 모읍니다. 본문을 노리로 바꿔 저장하면 낱말이 쪼개져 이 방식이 깨집니다. 그래서 기존 본문 칸은 그대로 두고 **노리용 하위 칸(`text.nori`)을 더한** 새 인덱스를 만들었습니다. 노리 검색은 후보를 더하는 데만 씁니다.

```bash
.venv/bin/python scripts/build-nori-index.py dict     # 사용자 사전 만들기
.venv/bin/python scripts/build-nori-index.py index    # 새 인덱스(기존 인덱스에서 복사, 원본은 그대로)
```

### 결과: 나빠지지 않았지만 좋아지지도 않았다

채택 기준(맞히던 질문을 놓치지 않을 것, MRR과 한 단어 검색 비율이 떨어지지 않을 것)을 실행 전에 적어 두고 비교했습니다.

| 지표 | 기존 | 노리 |
|---|---|---|
| 질문 22개 1위 적중 | 0.818 | 0.818 |
| 질문 22개 상위 5개 적중 | 1.0 | 1.0 |
| MRR | 0.898 | 0.898 |
| 한 단어 검색 비율 | 0.983 | 0.983 |

모든 지표가 같았습니다. 지금은 문서가 적어 기존 방식이 이미 거의 다 찾기 때문입니다. 그래서 노리는 **기본 꺼짐**으로 두고, 실제 문서를 올린 뒤 같은 기준으로 다시 잽니다. 알려진 위험도 있습니다. 노리 검색은 흔한 낱말 하나만 맞아도 후보로 넣으므로, 문서가 많아지면 관련 없는 조각이 후보 자리를 차지할 수 있습니다.

## 켜고 끄는 설정

| 설정 (`.env`) | 기본값 | 뜻 |
|---|---|---|
| `PARTS_SEMANTIC_SEARCH` | false | 부품 의미 검색(`kicad_parts_v2`). 실패하면 파일 카탈로그로 대체 |
| `PARTS_ONTOLOGY_INCLUDE_PROPOSED` | false | 승인 전 사전 개념도 질문 이해에 쓴다. 원칙은 승인된 개념만 |
| `PARTS_ROUTE_LOG` | true | 부품 경로 사용 기록(이 PC 전용, 크기 상한). **질문 원문이 남으므로 공유·외부 전송 금지.** 서버 프로세스에서만 기록하므로 평가 스크립트의 질문은 남지 않는다 |
| `DOCUMENT_NORI` + `ES_DOCUMENT_INDEX` | false / 기존 인덱스 | 노리 하위 칸이 있는 문서 인덱스와 노리 후보 검색 |

설정을 바꾼 뒤에는 서버를 재시작합니다(`systemctl --user restart langchain-lab`). 되돌릴 때는 `.env`의 해당 줄을 지우고 다시 재시작합니다.

## 검증 결과와 남은 한계

| 항목 | 상태 |
|---|---|
| 단위 테스트 | 통과 (Wikidata 모듈 9개, 노리 6개 포함, 서버·네트워크 없이 도는 것) |
| 노리 평가 | 기존과 모든 지표 같음 → 기본 꺼짐 |
| 부품 한국어 검색 | 독립 세트 3개 1회씩 평가, 세트마다 기준 하나씩 미달을 그대로 기록 |
| 부품 한국어 검색의 마지막 수정 | **미검증** (실제 사용 질문으로 확인 예정) |
| Wikidata 분야 거르기 | 남은 오류와 빠진 정답이 있음 → 근거 보조로만 사용 |

- 평가 질문과 정답은 모두 사람이 검토하기 전의 초안입니다. 세트 크기도 25~45개로 작습니다.
- 정답은 분류 단위입니다. 그 분류 안의 부품이면 모두 맞힌 것으로 칩니다.
- 사전에 없는 표현의 부품 질문은 부품 경로가 받지 못하고 원래 흐름(일반 대화)으로 갑니다. 해롭지는 않지만 부품 질문의 일부를 놓칩니다(세트 3에서는 44%).
- 한·영 후보 사전은 사람이 직접 승인한 것이 아닙니다(위임 승인 132개, 나머지 36개는 승인 전). 이 장을 쓰는 시점에 부품 한국어 검색은 시험용으로 켜져 있었고, 승인 전 개념도 함께 썼습니다.
- 문서 평가는 샘플 문서로 한 것이라 "나빠지지 않음"까지만 확인했습니다.

## 핵심 정리

1. 한국어 질문과 영어 부품 자료 사이에는 낱말 검색으로 메울 수 없는 간격이 있다(적중 0.000).
2. 개념 그래프는 항목마다 출처(버전·근거 부품 수)를 달아야 검토할 수 있다.
3. 공개 사전(Wikidata)은 근거 보조로 쓸 만하지만, 같은 낱말의 다른 분야 항목을 걸러야 하고, 한국어 전문 용어는 적다.
4. 답은 모델이 아니라 코드가 카탈로그 값으로 쓴다.
5. 평가는 독립 질문으로 한 번만, 기준은 실행 전에 적고, 미달도 그대로 기록한다.
6. 새 기능(노리)은 기존 동작을 깨지 않게 옆에 붙이고, 이득이 확인될 때까지 꺼 둔다.
