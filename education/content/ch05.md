## 배경 개념: 공개 페이지와 내 PC의 역할

GitHub Pages는 정적 파일만 제공하므로 Python 모델 서버를 대신 실행할 수 없습니다. 그래서 공개 페이지와 로컬 서비스의 역할을 나눴습니다.

```text
https://yuul-jung.github.io/langchain-lab/      (공개, 누구나)
   ├─ index.html          로컬 실행 게이트: 명령 복사 + 로컬 주소 링크
   └─ education/dist/     이 교재 (rule_md 교육용 HTML 표준)

http://127.0.0.1:8000/                          (내 PC 에서만)
   ├─ /                   채팅 (자동 · 문서만 · 일반만, 제4장)
   └─ /documents          문서 관리자 (제2장)
```

이 장은 제1장의 "GitHub 배포 구조" 절을 독립시킨 것입니다. 교재 v07에서 장을 나누면서 내용은 그대로 옮기고, 그 뒤에 추가된 업데이트 완료 판정과 교재 게시 구조만 새로 썼습니다.

## 명령 세 개와 스크립트

공개 페이지의 **명령 복사** 버튼이 주는 세 명령:

```bash
# ① 처음 한 번: 기본 세팅 (프로젝트가 없으면 내려받고, 있으면 최신 코드로 갱신 · 다시 실행해도 안전)
if [ -d ~/langchain_web/.git ]; then git -C ~/langchain_web pull --ff-only origin main; else git clone https://github.com/Yuul-Jung/langchain-lab.git ~/langchain_web; fi && bash ~/langchain_web/scripts/setup-local.sh

# 평소 실행 (매번 이 명령 하나)
cd ~/langchain_web && bash scripts/start-local.sh

# 소스 업데이트 (GitHub에 새 버전이 올라왔을 때)
cd ~/langchain_web && bash scripts/update-local.sh
```

처음 배포한 명령은 폴더가 있으면 갱신 없이 바로 실행해, `setup-local.sh`가 추가되기 전 코드가 있던 PC에서 `No such file or directory`로 실패했습니다(2026-11-12 실측). 지금 명령은 폴더가 있으면 먼저 `git pull --ff-only`를 하고, 로컬 수정과 충돌하면 세팅을 실행하지 않고 멈춥니다.

미리 필요한 것은 **LM Studio**(DeepSeek-R1-Distill-Qwen-14B, Qwen3-Embedding-4B 내려받기)와 **Elasticsearch 9** 설치입니다. 이 둘은 관리자 권한과 대용량 내려받기가 필요해 스크립트가 대신 설치하지 않고, 빠졌으면 무엇이 빠졌는지와 조치 명령을 알려 줍니다.

| 스크립트 | 하는 일 | 하지 않는 일 |
|---|---|---|
| `setup-local.sh` | ① 필수 프로그램(git·python3·venv·systemd·lms·9200 포트) ② CA 인증서 ③ `.env` 없으면 비밀번호 입력 ④ `update-local.sh` ⑤ LM Studio 서버 시작, 임베딩·채팅 모델이 안 올라가 있으면 로드 ⑥ `/api/status` 최종 상태 출력 | `sudo` 자동 실행, 기존 `.env` 덮어쓰기, 이미 올라간 모델 내리기 |
| `update-local.sh` | ① `git pull --ff-only` ② 가상환경 확인 ③ 패키지 설치 ④ 구문 검사 ⑤ 오프라인 단위 테스트 ⑥ 서비스 재시작 ⑦ 문서 API·연결 진단 | 검사가 하나라도 실패하면 서버를 재시작하지 않음 |
| `start-local.sh` | LM Studio가 꺼져 있으면 `lms server start`, FastAPI 서비스 시작, 포트 3개 점검, 연결 진단 | 패키지 재설치, 데이터·인덱스·비밀번호 변경, 자동 `sudo` |

## 다른 PC로 옮길 준비

소스코드는 GitHub에 있지만, 문서 목록·평가 자료(`data/`), 업로드 원본(`uploads/`), 비밀번호와 설정(`.env`)은 GitHub에 올라가지 않습니다. 다른 PC로 옮기려면 이 셋을 직접 가져가야 합니다. 검색 색인(Elasticsearch)은 옮기지 않고 새 PC에서 다시 만듭니다.

```bash
# 무엇이 묶이는지만 보기 (파일을 만들지 않음)
bash scripts/backup-local-data.sh --list

# 묶음 만들기: 기본 위치는 홈 폴더의 langchain-lab-backup-날짜-시각.tar.gz
bash scripts/backup-local-data.sh
```

| 장치 | 동작 |
|---|---|
| 저장 위치 | 프로젝트 폴더 안에는 만들지 않습니다(실수로 GitHub에 올라갈 수 있음). |
| 덮어쓰기 | 같은 이름의 파일이 있으면 멈춥니다. |
| 권한 | 본인만 읽을 수 있게(600) 만듭니다. 묶음에는 비밀번호와 비공개 문서가 들어 있습니다. |
| 원본 | 지우거나 바꾸지 않습니다. |

옮긴 PC에서의 순서:

```text
① 기본 세팅            공개 시작 페이지의 "기본 세팅" 명령 (scripts/setup-local.sh)
      ↓
② 묶음 풀기            tar -xzf 묶음파일.tar.gz -C ~/langchain_web
      ↓
③ Elasticsearch 비밀번호  새 PC의 비밀번호는 다르므로 scripts/repair-es-auth.py
      ↓
④ 서비스 재시작         systemctl --user restart langchain-lab
      ↓
⑤ 색인 다시 만들기      문서 관리 화면 "07 · 추출 규칙 변경 반영" → 변경 미리보기 → "색인 없음" 문서 다시 추출
```

실측 (2026-11-12):

| 확인 | 결과 | 판정 |
|---|---|---|
| 묶음 스크립트 | 가짜 프로젝트 폴더로 단위 테스트 6개: 내용물, 권한 600, 프로젝트 안 저장 거절, 덮어쓰기 거절, 원본 불변 | 통과 |
| 실제 프로젝트 | `--list`만 실행: data 18개 파일(208K), uploads 8개 파일(20M), .env. **실제 묶음은 만들지 않음** | 미리보기만 |
| ⑤ 색인 다시 만들기 | 문서 목록·원본의 임시 복사본 + 빈 임시 색인: 8개 모두 "색인 없음"으로 표시, 일괄 실행 21.7초, 199청크, 검색 정상 | 통과 (임시) |
| ①~④를 실제 다른 PC에서 | 다른 PC가 준비되지 않음 | 미검증 |

다시 만든 색인은 지금 추출 규칙을 따르므로, 예전 규칙으로 색인되어 있던 문서는 조각이 달라질 수 있습니다(제2장 "여러 문서 한 번에 다시 추출"의 주의 참고).

## 공개 페이지 버튼으로 내 PC에서 실행

웹페이지는 브라우저 보안 때문에 PC 프로그램을 직접 실행할 수 없습니다. 그래서 기본 세팅 6단계가 현재 사용자 계정에 `langchainlab://` **링크 처리기**를 한 번 등록합니다. 그 뒤로는 공개 페이지 버튼으로 실행합니다.

```text
공개 페이지 버튼 (href="langchainlab://start")
   ↓  Chrome 확인창 "xdg-open 열기" → 허용
Ubuntu 링크 처리기 (~/.local/share/applications/langchainlab-launcher.desktop)
   ↓
scripts/url-launcher.sh  ── 허용 목록: start · update · setup
   ↓
터미널 창에서 start-local.sh / update-local.sh / setup-local.sh 실행
   ↓  (동시에) 공개 페이지가 4초마다 /api/status 확인 → "완료: 모두 정상입니다"
```

| 버튼 | 실행 스크립트 | 하는 일 |
|---|---|---|
| ▶ 로컬 서비스 시작 | `start-local.sh` | FastAPI·LM Studio 서버 시작, 채팅·임베딩 모델 로드 |
| ⟳ 최신 버전으로 업데이트 | `update-local.sh` | GitHub 최신 코드, 테스트, 서비스 재시작 |
| ⚙ 기본 세팅 다시 실행 | `setup-local.sh` | 전체 점검·세팅 |

**파일** `scripts/url-launcher.sh` · 원본 발췌 · 주입 시험 통과

```bash
url="${1:-}"
# langchainlab://start , langchainlab://start/ , langchainlab:start 모두 허용
action="${url#langchainlab:}"
action="${action#//}"
action="${action%%[/?#]*}"

case "$action" in
  start)  script="start-local.sh";  title="LangChain Lab · 서비스 시작" ;;
  update) script="update-local.sh"; title="LangChain Lab · 업데이트" ;;
  setup)  script="setup-local.sh";  title="LangChain Lab · 기본 세팅" ;;
  *)
    printf '%s 거부된 요청: %q\n' "$(date '+%F %T')" "$url" >>"$LOG"
    ...
    exit 2
    ;;
esac
```

**코드 풀이**

- 링크 주소는 어느 웹사이트에서나 만들 수 있으므로 **동작 이름 세 개만** 받습니다. 주소의 나머지(경로·인자·쿼리)는 쓰지 않고 셸에 넘기지 않습니다.
- `langchainlab://start;touch …`, `langchainlab://$(…)`, 다른 사이트 주소 등 주입 시도 9종을 시험해 모두 거부되고 `~/.local/state/langchain-lab/launcher.log`에 기록되는 것을 확인했습니다.
- 실행 전에 Chrome이 반드시 확인창을 띄웁니다. "항상 허용"에 체크하면 이 사이트에서는 다음부터 묻지 않습니다.
- 해제: `rm ~/.local/share/applications/langchainlab-launcher.desktop`

실측 기록 (2026-11-12):

```text
$ tail -3 ~/.local/state/langchain-lab/launcher.log
2026-11-12 16:49:57 실행: start
2026-11-12 16:51:28 실행: start
```

## 공개 페이지에서 내 PC 상태 확인

공개 시작 페이지의 **③ 로컬 프로그램 상태 확인** 버튼은 브라우저에서 `http://127.0.0.1:8000/api/status`에 상태만 묻습니다. 서비스가 실행 중인 바로 그 PC의 브라우저에서만 동작하고, Chrome이 "로컬 네트워크 기기 접근"을 물으면 허용합니다.

**파일** `local_status.py` · 원본 발췌 · 단위 테스트 통과

```python
def cors_headers(path: str, origin: str | None, method: str,
                 private_network: bool = False) -> dict | None:
    """허용된 출처의 /api/status 요청에만 CORS 헤더를 돌려준다. 그 외는 None."""
    if path != STATUS_PATH or not origin or origin not in ALLOWED_STATUS_ORIGINS:
        return None
    headers = {"Access-Control-Allow-Origin": origin, "Vary": "Origin"}
    if method == "OPTIONS":
        headers["Access-Control-Allow-Methods"] = "GET"
        headers["Access-Control-Max-Age"] = "600"
        # 공개 사이트 → 내 PC(루프백) 요청에 대한 Chrome 사설망 접근 사전 확인 응답
        if private_network:
            headers["Access-Control-Allow-Private-Network"] = "true"
    return headers
```

**코드 풀이**

- 공개 페이지가 읽을 수 있는 것은 `/api/status` **하나, GET 하나**뿐입니다. 채팅·업로드·문서 목록은 공개 페이지에서 호출할 수 없습니다.
- 허용 출처는 `https://yuul-jung.github.io` 하나이며 환경변수 `STATUS_ALLOWED_ORIGINS`로 바꿀 수 있습니다.
- 응답에는 모델 ID·로드 상태·버전·조치 명령만 들어갑니다. 문서 내용, 파일명, 비밀번호는 넣지 않습니다.

실측 화면 (2026-11-12, 공개 페이지 → 내 PC):

```text
✅ FastAPI         127.0.0.1:8000 응답
✅ LM Studio       로드됨: deepseek-r1-distill-qwen-14b, text-embedding-qwen3-embedding-4b
✅ 채팅 모델       deepseek-r1-distill-qwen-14b 로드됨
✅ 임베딩 모델     text-embedding-qwen3-embedding-4b 로드됨
✅ Elasticsearch   연결됨 9.5.6
모두 정상입니다. 아래 ② 로컬 AI 채팅을 열어 사용하세요.
```

같은 날 제3장 작업 직후에는 비전 모델 `qwen3-vl-4b`(컨텍스트 16384)만 올라가 있어, RAG 질문이 `502 LM Studio 모델 응답 실패`로 끝났습니다. LM Studio가 돌려준 원인은 `Failed to load model "deepseek-r1-distill-qwen-14b"`였습니다. 노트북 한 대에서 비전 모델과 14B 채팅 모델이 메모리를 다툰 것입니다. 이제 이 상태에서는 상태 확인이 ⚠️와 함께 다음 명령을 안내하고, 채팅 오류 메시지에도 같은 원인과 명령이 붙습니다.

```bash
# 로드된 모델 확인 후, 비전 모델이 있으면 내리고 채팅 모델이 없을 때만 올림 (여러 번 실행해도 안전)
lms ps
lms ps | grep -q qwen3-vl-4b && lms unload qwen3-vl-4b
lms ps | grep -q deepseek-r1-distill-qwen-14b || lms load deepseek-r1-distill-qwen-14b
```

이미 올라가 있는 모델에 `lms load`를 다시 실행하면 같은 모델을 하나 더 올리려다 `unable to allocate CUDA0 buffer`(GPU 메모리 부족)로 실패합니다. 기존 모델은 그대로 남으므로 위처럼 `lms ps`로 확인한 뒤 필요한 것만 실행합니다(2026-11-12 실측).

실패하면 아래 순서로 원인을 좁힙니다.

| 화면 표시 | 원인 | 조치 |
|---|---|---|
| ❌ 로컬 서비스에 연결하지 못했습니다 | FastAPI 꺼짐 | `bash scripts/start-local.sh` |
| 〃 | 상태 API가 없는 이전 버전 | `bash scripts/update-local.sh` |
| 〃 | 브라우저가 로컬 접근 차단 | 사이트 설정 → 로컬 네트워크 액세스 허용 |
| ⚠️ 채팅 모델 미로드 + 다른 모델 로드됨 | 메모리 경합 | 안내된 `lms unload … && lms load …` (이 상태에서만 실행) |
| `unable to allocate CUDA0 buffer` | 이미 올라간 모델을 한 번 더 로드 | 무시해도 됨, `lms ps`로 기존 모델 확인 |

## 업데이트 완료 판정: 실행 버전 비교

공개 페이지의 **⟳ 최신 버전으로 업데이트** 버튼은 처음에 4초 만에 "업데이트 완료"를 표시했습니다. 누르기 전에도 상태가 이미 정상이었기 때문에, 업데이트가 실제로 반영되기 전에 첫 확인에서 바로 "정상"으로 끝난 것입니다(2026-11-12 17:20 수정).

동작 순서 (커밋 번호는 설명용 예시):

```text
버튼 클릭 전   /api/status → version: 1111111   (지금 실행 중인 커밋 기억)
      ↓  langchainlab://update → update-local.sh (pull · 테스트 · 재시작)
4초마다 확인   version 이 그대로면 "진행 중"
      ↓
version: 2222222 (바뀜) + 모든 항목 정상 → "업데이트 완료 · 버전 1111111 → 2222222"
5분 안에 바뀌지 않으면 → Chrome 확인창·터미널 오류를 확인하라고 안내
```

버전 항목이 없는 이전 서버에서 업데이트하면 "이전 → 새 커밋"으로 표시됩니다.

**파일** `app.py` · 원본 발췌

```python
def _app_version():
    """(추가) 실행 중인 코드의 Git 커밋 번호. 업데이트가 실제로 반영됐는지 화면에서 확인하는 데 쓴다."""
    import subprocess
    try:
        out = subprocess.run(["git", "-C", str(ROOT), "rev-parse", "--short", "HEAD"],
                             capture_output=True, text=True, timeout=3)
        return out.stdout.strip() or "unknown"
    except (OSError, subprocess.SubprocessError):
        return "unknown"


APP_VERSION = _app_version()
```

**파일** `index.html` (공개 시작 페이지) · 원본 발췌

```javascript
const before=lastVersion;   // 버튼을 누르기 전 실행 버전
...
const changed=!isUpdate||(lastVersion&&lastVersion!==before);
if(ok&&changed){ /* 완료 표시: 버전 이전 → 이후 */ }
else if(sec>=(isUpdate?300:180)){ /* 시간 초과 안내 */ }
```

**코드 풀이**

## 접근 제어: 이 PC 전용과 비밀번호 로그인

지금까지 이 서비스의 보호 장치는 "서버를 `127.0.0.1`에만 연다" 하나였습니다. 다른 기기에서 쓰려는 계획(AI PC, 리버스 프록시)을 준비하면서 접근 제어를 넣었고(2026-11-12), 그 과정에서 `127.0.0.1` 전용 서버에도 있던 틈 세 개를 함께 막았습니다.

| 틈 | 수법 | 막는 방법 |
|---|---|---|
| 다른 웹사이트가 내 서버의 응답을 읽음 | 악성 페이지가 자기 도메인을 `127.0.0.1`로 바꿔, 내 브라우저가 내 서버에 같은 사이트처럼 요청하게 함 (DNS 리바인딩) | 로그인 없이 받는 요청은 주소 이름(Host)이 `127.0.0.1`·`localhost`일 때만 허용 |
| 다른 웹사이트가 내 서버에 쓰기 요청을 보냄 | 악성 페이지가 내 브라우저로 업로드·재추출 요청을 보냄 (CSRF) | 변경을 일으키는 요청은 보낸 페이지의 주소(Origin)가 서버 주소와 같을 때만 허용 |
| 다른 웹사이트가 내 서버를 바쁘게 만듦 | 응답은 읽지 못해도, 무거운 읽기 요청(재추출 미리보기)을 뒤에서 반복 호출 | 다른 사이트의 페이지가 뒤에서 보내는 요청은 `/api/status`만 허용 (브라우저의 `Sec-Fetch-*` 표시로 판단) |

판정 규칙:

| 상황 | `ACCESS_PASSWORD` 없음 (기본) | `ACCESS_PASSWORD` 있음 |
|---|---|---|
| 서버가 실행 중인 PC에서 접속 | 허용 | 허용 (로그인 없음) |
| 다른 기기에서 접속 | **거절 (403)** — 서버를 실수로 외부에 열어도 | `/login`으로 보냄, API는 401 |
| 다른 기기에서 로그인한 뒤 | — | 허용 (세션 12시간) |
| 주소 이름이 `127.0.0.1`·`localhost`가 아닌 로컬 요청 | 거절 (403) | 거절 (403) |
| 다른 웹사이트에서 온 POST | 거절 (403) | 거절 (403), 로그인한 상태여도 |
| 다른 웹사이트의 페이지가 뒤에서 보낸 요청 (`/api/status` 제외) | 거절 (403) | 거절 (403) |
| 다른 웹사이트의 링크를 눌러 새 탭으로 열기 | 허용 | 로그인 규칙에 따름 |

**파일** `access_control.py` · 원본 발췌 · 단위 테스트 36개 통과

```python
def same_origin(origin_header: str | None, host_header: str | None, allowed_hosts=()) -> bool:
    """Origin 이 없거나(브라우저가 아님) 이 서버의 주소와 같으면 True."""
    if origin_header is None:
        return True
    origin_host = host_name(urlsplit(origin_header).netloc)
    if not origin_host:
        return False            # 'null' 등: 출처를 알 수 없는 페이지
    return origin_host == host_name(host_header) or origin_host in {h.lower() for h in allowed_hosts}


def cross_site_background(path: str, fetch_site: str | None, fetch_mode: str | None,
                          fetch_dest: str | None) -> bool:
    """다른 사이트의 페이지가 뒤에서 보낸 요청인지 (새 탭·창으로 여는 것은 아님).

    Sec-Fetch-* 가 없는 요청(curl, 오래된 브라우저)은 판단하지 않는다.
    """
    if (fetch_site or "").lower() != "cross-site" or path in CROSS_SITE_PATHS:
        return False
    top_level_navigation = (fetch_mode or "").lower() == "navigate" and (fetch_dest or "").lower() == "document"
    return not top_level_navigation


def decide(*, path: str, client_host: str | None, host_header: str | None,
           password_set: bool, authenticated: bool,
           require_loopback_auth: bool = False, allowed_hosts=(),
           method: str = "GET", origin_header: str | None = None,
           fetch_site: str | None = None, fetch_mode: str | None = None,
           fetch_dest: str | None = None) -> str:
    """요청을 어떻게 처리할지: allow · login(로그인 페이지로) · unauthorized(401) · forbidden · bad_host · bad_origin(403).

    순서가 중요하다. 로그인 없이 통과시키는 경우(루프백 신뢰)에만 Host 를 검사한다.
    """
    if method.upper() in UNSAFE_METHODS and not same_origin(origin_header, host_header, allowed_hosts):
        return "bad_origin"
    if cross_site_background(path, fetch_site, fetch_mode, fetch_dest):
        return "bad_origin"
    local = is_loopback(client_host)
    if not password_set:
        if not local:
            return "forbidden"          # 비밀번호가 없으면 이 PC 밖에서는 쓸 수 없다
        trusted = True
    else:
        if path in OPEN_PATHS or authenticated:
            return "allow"
        trusted = local and not require_loopback_auth
        if not trusted:
            return "unauthorized" if path.startswith("/api/") else "login"
    if trusted and host_name(host_header) not in LOOPBACK_HOSTS | {h.lower() for h in allowed_hosts}:
        return "bad_host"
    return "allow"
```

**코드 풀이**

- 판정 함수는 웹 서버에 의존하지 않는 순수 함수라, 서버 없이 모든 경우를 테스트합니다. 규칙을 일부러 망가뜨리면(Origin 검사를 끔, 모든 주소를 이 PC로 취급 등) 테스트가 3~5개씩 실패하는 것을 확인했습니다.
- 주소 이름(Host) 검사는 **로그인 없이 통과시키는 요청에만** 합니다. 로그인한 세션은 쿠키가 그 주소에 묶여 있어 다른 도메인에서 쓸 수 없습니다.
- `curl`처럼 Origin이 없는 요청은 브라우저가 아니므로 CSRF 검사 대상이 아닙니다. `scripts/`의 점검 명령이 그대로 동작합니다.
- 세션은 서버에 저장하지 않습니다. `만료시각.서명` 값을 쿠키에 두고 HMAC으로 검증합니다. 쿠키는 `HttpOnly`(페이지의 스크립트가 읽지 못함), `SameSite=Strict`(다른 사이트에서 보낸 요청에 실리지 않음)입니다.
- 비밀번호 비교는 걸리는 시간으로 추측하지 못하게 일정 시간 비교를 쓰고, 같은 주소에서 5번 틀리면 5분 동안 로그인 시도를 막습니다.

설정 (`.env`, 바꾼 뒤 서비스 재시작):

| 설정 | 기본값 | 뜻 |
|---|---|---|
| `ACCESS_PASSWORD` | 비어 있음 | 비우면 이 PC 전용. 넣으면 다른 기기는 `/login`에서 이 비밀번호로 로그인 |
| `SESSION_HOURS` | `12` | 로그인 유지 시간 |
| `SESSION_SECRET` | 비어 있음 | 비우면 서버를 시작할 때마다 새로 만듭니다(재시작하면 다시 로그인). |
| `AUTH_REQUIRE_LOOPBACK` | `false` | 같은 PC에 리버스 프록시를 두면 모든 요청이 이 PC에서 온 것으로 보이므로 `true` |
| `AUTH_COOKIE_SECURE` | `false` | HTTPS로만 접속할 때 `true` |
| `ALLOWED_HOSTS` | 비어 있음 | 로그인 없이 쓸 때 허용할 추가 주소 이름, 프록시 도메인 |

**다른 기기에서 실제로 접속하려면 (미검증)** — 비밀번호를 넣는 것만으로는 다른 기기에서 접속되지 않습니다. 서버가 아직 `127.0.0.1`에만 열려 있기 때문입니다. `scripts/install-service.sh`의 `--host 127.0.0.1`을 그 네트워크의 주소로 바꿔야 하며, 이 부분은 바꾸지 않았고 다른 기기에서의 접속도 시험하지 않았습니다. 신뢰할 수 없는 네트워크에서는 HTTPS 리버스 프록시를 거쳐야 합니다. 평문 HTTP에서는 비밀번호가 암호화되지 않은 채 전송됩니다.

**한계**

- 사용자별 계정이 아니라 비밀번호 하나를 함께 쓰는 방식입니다. 문서별 접근 권한은 없습니다.
- 같은 PC에 리버스 프록시를 두고 `AUTH_REQUIRE_LOOPBACK=true`로 하면 `scripts/`의 점검 명령도 로그인이 필요해지는데, 스크립트의 로그인 처리는 만들지 않았습니다.
- 요청 횟수 제한은 로그인에만 있습니다. 업로드·채팅의 사용량 제한은 없습니다. 리버스 프록시 뒤에서는 모든 사용자가 같은 주소로 보이므로, 한 사람이 5번 틀리면 모두의 로그인이 5분 동안 막힙니다.
- `Sec-Fetch-*` 표시가 없는 오래된 브라우저에서는 세 번째 보호가 동작하지 않습니다.

## 운영 중 메모리 부족: 서비스가 갑자기 멈췄을 때

**증상** — 채팅이 오류를 내거나, 문서 검색이 "연결 실패"를 냅니다. 상태 확인 페이지에서 Elasticsearch나 LM Studio가 ❌로 나옵니다.

**실제로 있었던 일** (2026-11-14 새벽) — Elasticsearch가 0시 52분에, LM Studio의 모델 서버(`llama-server`)가 1시 0분에 운영체제의 메모리 부족 종료기(OOM killer)에 강제로 종료됐습니다. 복구해서 LM Studio를 다시 올리자 Elasticsearch가 1시 15분에 또 종료됐습니다.

| 확인한 사실 | 값 |
|---|---|
| 이 PC의 메모리 | 31GB |
| 종료 당시 Elasticsearch가 쓴 메모리 | 최대 약 16GB (14.2GB를 쓰는 중에 종료) |
| 원인으로 보는 것 | Elasticsearch의 힙(JVM 메모리) 상한이 없어 전체의 절반을 자동으로 잡음 + LM Studio 모델(대화 14B · 임베딩 · 비전)이 함께 올라감 + 같은 시간대의 평가 실험(임시 서버·평가 동시 실행) |

실험이 원인의 전부였는지는 확인하지 못했습니다. 상한이 없는 상태에서는 평소 사용만으로도 다시 일어날 수 있는 구조입니다.

**진단** — 모두 읽기만 합니다.

```bash
systemctl is-active elasticsearch                                      # active 가 아니면 종료된 것
curl -s http://127.0.0.1:8000/api/status | python3 -m json.tool        # 어느 구성요소가 ❌인지
journalctl -k --since "-1h" --no-pager | grep -i "killed process"      # 메모리 부족으로 종료된 프로세스
free -h                                                                # 사용 가능한 메모리
ps -eo pid,rss,comm --sort=-rss | head -5                              # 메모리를 가장 많이 쓰는 프로세스
```

**복구**

- Elasticsearch: `systemctl start elasticsearch`. 이 PC에서는 관리자 비밀번호 없이 시작할 수 있었지만, 다른 PC에서는 다를 수 있습니다. 시작 뒤 문서 개수가 그대로인지 확인합니다(이번에는 문서 9개·청크 236개가 그대로였습니다).
- LM Studio: 화면 앱이라 직접 앱을 켜고 모델을 올립니다. 터미널의 `lms` 명령은 실행 중인 앱이나 설치를 찾지 못했습니다.
- 메모리 상한 없이 Elasticsearch만 다시 켜면 LM Studio가 다시 종료될 위험이 큽니다. 상한을 먼저 정하는 편이 안전합니다.

**재발 방지: Elasticsearch 힙 상한** — 관리자 권한이 필요합니다.

```bash
sudo mkdir -p /etc/elasticsearch/jvm.options.d
printf -- '-Xms4g\n-Xmx4g\n' | sudo tee /etc/elasticsearch/jvm.options.d/heap.options
sudo systemctl restart elasticsearch
```

- 하는 일: Elasticsearch가 쓸 수 있는 메모리를 4GB로 제한하고 다시 켭니다. 색인 데이터는 건드리지 않습니다.
- 결과: Elasticsearch가 쓰는 메모리 **약 15GB → 4.6GB**, 사용 가능한 메모리 약 8.5GB(확인한 값).
- 4GB가 충분한지는 **지금 데이터(문서 9개, 청크 236개)에서 동작하는 것만 확인**했습니다. 문서가 크게 늘면 값을 다시 정합니다.
- 되돌리기: `sudo rm /etc/elasticsearch/jvm.options.d/heap.options` 후 서비스를 재시작합니다.

**실험할 때의 습관** — 무거운 평가나 임시 서버는 **한 번에 하나만** 돌립니다. 시작 전에 `free -h`로 여유를 확인합니다. 두 개를 동시에 돌려 전후를 비교하고 싶어도, 메모리가 모자라 서비스가 죽으면 비교 자체가 무효가 됩니다(제6장).

## 교재 생성과 게시

**교재 생성** — 이 교재는 [Yuul-Jung 교육용 HTML 표준](https://github.com/Yuul-Jung/rule_md/tree/main/web/education-html)의 생성기로 만듭니다. 원고는 Markdown이고, 생성된 HTML에 이미지·스타일·스크립트가 모두 들어 있어 파일 하나로 열립니다.

```bash
# 교재 생성 도구 설치 (교재를 고칠 때만 필요)
cd ~/langchain_web
.venv/bin/python -m pip install mistune

# education/course.json + content/ch0N.md → education/dist/*.html
cd education && ../.venv/bin/python build.py
```

실측 출력 (2026-11-12, 교재 v07: 목차 + 5장 구성):

```text
생성 완료: 6 개 HTML 파일
  …/education/dist/ch01_local_ai_rag_foundation_v07.html
  …/education/dist/ch02_document_ingestion_v02.html

  …/education/dist/ch04_settings_model_selection_v01.html

  …/education/dist/index.html
```

장을 고치면 `course.json`에서 그 장의 `version`을 `v02`로 올립니다. 생성기는 `dist/`의 이전 버전 파일을 지웁니다.

GitHub Pages는 저장소 `main` 브랜치의 루트 폴더를 그대로 게시합니다. 공개 주소별 역할은 다음과 같습니다.

| 공개 주소 | 내용 |
|---|---|
| `/` (`index.html`) | 시작 페이지: 실행 버튼, 상태 확인, 교재 바로가기 |
| `/education/dist/index.html` | 이 교재의 목차 페이지 |
| `/education/dist/ch0N_…_vNN.html` | 장별 교재 (최신 버전 하나만 존재) |
| `/education/assets/diagrams/*.svg` | 교재 구조도 그림 |
| `/docs/*.html` (예전 교재) | v07부터 내용 대신 표준 교재 해당 장으로 자동 이동 |

예전 `docs/` 교재(제1장 구축 가이드 2종, 제2장 안내서, 구조도 디자인 표준)는 내용이 표준 교재 제1·2장과 겹치고, 돌아가기 링크가 교재 목차가 아니라 시작 페이지로 연결되어 있었습니다. 구조도 6종은 SVG 그림으로 다시 그려 제1·2장에 넣었고, 예전 주소로 들어오면 해당 장으로 이동합니다. 예전 파일 원본은 Git 기록에 남아 있습니다. 구조도의 CSS 원본 `docs/diagram-components.css`는 링크로 열면 페이지가 아니라 CSS 원문이 보이던 파일이라 게시에서 내렸습니다.

## 핵심 정리

- GitHub Pages는 정적 파일만 제공합니다. 공개 페이지는 명령 안내·실행 버튼·상태 확인만 하고, 모델과 검색은 내 PC(`127.0.0.1`)에서만 동작합니다.
- 실행 버튼은 `langchainlab://start|update|setup` 세 동작만 받는 실행기로 연결되고, 실행 전에 Chrome이 반드시 확인을 받습니다.
- 공개 페이지가 내 PC에서 읽을 수 있는 것은 `/api/status` 하나뿐이며, 응답에는 모델·상태·버전만 들어갑니다.
- 업데이트는 실행 버전(커밋 번호)이 실제로 바뀌어야 완료로 표시합니다.
- 교재는 목차 페이지와 장별 최신 버전 하나만 게시하고, 예전 주소는 해당 장으로 이동시킵니다.
- GitHub에 없는 자료(`data/`, `uploads/`, `.env`)는 묶음 스크립트로 옮기고, 색인은 새 PC에서 다시 만듭니다.
- Elasticsearch는 메모리 상한을 정하지 않으면 전체 메모리의 절반을 잡아 LM Studio와 함께 쓸 때 메모리 부족으로 종료될 수 있습니다. 상한을 두고, 무거운 실험은 한 번에 하나만 돌립니다.
- 서비스는 기본적으로 이 PC에서만 쓸 수 있고, 접속 비밀번호를 넣으면 다른 기기는 로그인해야 합니다. 주소 이름과 Origin 검사로 다른 웹사이트를 통한 접근을 막습니다.
