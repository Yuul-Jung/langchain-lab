## 배경 개념: 검색 품질은 재야 고칠 수 있다

제2장까지 만들면 문서가 색인되고 검색 결과가 나옵니다. 그런데 실제로 써 보면 "검색이 제대로 안 된다"는 느낌이 듭니다. 이 장은 2026-11-12 하루 동안 그 느낌을 **증상 → 원인 → 측정 → 수정 → 다시 측정**으로 바꾼 기록입니다.

실제로 보고된 증상은 세 가지였습니다.

| 증상 (사용자 보고) | 실제 원인 | 고친 방법 |
|---|---|---|
| 채팅이 업로드한 문서로 답하지 않는다 | 채팅 RAG가 제1장 실습 문장 3개만 검색 | 검색 대상을 업로드 문서로 변경 |
| 관련된 문서의 쪽을 거의 다 가져온다 | 벡터 검색은 관련이 없어도 요청한 개수를 채움 | 1위와 점수 차이가 큰 결과를 숨김 |
| 한 단어로 검색하면 엉뚱한 쪽이 나온다 | 짧은 검색어에서는 벡터 유사도가 뜻을 잘 구분하지 못함 | 검색어가 본문에 실제로 있는지를 점수에 반영 |

세 번 모두 서버·모델·Elasticsearch는 정상이었습니다. **연결 상태가 정상이라는 것과 검색 품질이 좋다는 것은 별개**입니다.

이후(2026-11-13~14)에는 검색이 맞은 **뒤의 답변 단계**를 같은 방식으로 다뤘습니다. 문제 5~8은 답변의 외국 문자·근거·출처, 문제 9는 질문을 문서로 보낼지 정하는 판단입니다. 판단 규칙은 정할 때 쓴 질문의 수치가 낙관적이었다는 것을 새 질문으로 확인한 기록이 들어 있습니다.

이 장에서 지킨 원칙:

1. 원인을 추정하지 않고, 같은 질문을 넣어 실제 순위와 점수를 확인합니다.
2. 고치기 전에 **색인을 바꾸지 않는 실험**으로 효과를 먼저 잽니다.
3. 수치가 좋아지지 않은 방법은 채택하지 않고, 왜 버렸는지 남깁니다.
4. 바꾼 값은 `.env`에서 끌 수 있게 합니다.

검색 품질을 재는 지표:

| 지표 | 뜻 | 좋을수록 |
|---|---|---|
| hit@1 | 정답 쪽이 1위인 질문의 비율 | 높게 |
| hit@k (정답 포함) | 정답 쪽이 결과 안에 있는 질문의 비율 | 높게 |
| MRR | 정답이 처음 나온 순위의 역수 평균 (1위 1.0, 2위 0.5, 없음 0) | 높게 |
| 정밀도 | 보여 준 결과 중 정답 쪽의 비율 | 높게 |
| 평균 결과 수 | 질문 하나에 보여 준 결과 개수 | 정답을 잃지 않는 한 적게 |
| 낱말 포함률 | 한 단어 검색에서, 결과 본문에 그 낱말이 실제로 있는 비율 | 높게 |

## 전체 흐름

```text
질문
  ↓  Qwen3 임베딩 (2,560차원)
┌─ 벡터 후보 30개 ── Elasticsearch kNN (cosine)
└─ 낱말 후보 30개 ── 질문 낱말이 본문에 들어 있는 청크 (wildcard)

문서 검색 화면: 검색어 주변 발췌 + 점수 내역     채팅 RAG: 근거로 전달 (문서명·쪽 번호 포함)
```

## 평가 세트와 채점 도구

고치기 전에 "지금 얼마나 되는지"를 숫자로 만들어야 합니다. 질문·정답·근거 쪽을 한 줄에 하나씩 적습니다.

**파일** `data/eval/questions.jsonl` · 형식 (내용은 지어낸 예시)

```json
{"id": "q01", "question": "실습 장비는 몇 대 필요해?", "document_id": "a1b2c3", "pages": [4, 12], "answer": "3대", "keywords": ["장비"], "status": "draft"}
```

| 항목 | 뜻 |
|---|---|
| `document_id` | 문서 ID. 앞 6자리만 써도 됩니다. |
| `pages` | 근거가 있는 원본 쪽 번호. 여러 쪽이면 모두 적습니다. |
| `status` | `draft`(초안) 또는 `approved`(사람이 정답과 쪽을 확인함) |

질문을 쓸 때의 주의:

- 문서의 문장을 그대로 베끼지 않고 학습자가 물을 법한 말로 씁니다. 문장을 베끼면 뜻으로 찾는 능력이 아니라 같은 글자를 찾는 능력을 재게 됩니다.
- 숫자·이름·명령처럼 정답이 분명한 사실을 고릅니다.
- 초안을 쓴 뒤 "정답이라고 적은 쪽에 핵심어가 실제로 있는지"를 기계적으로 확인합니다. 정답 쪽이 틀리면 채점 자체가 틀립니다.

한 단어 검색은 `data/eval/keywords.txt`에 낱말을 한 줄씩 적습니다. 정답 기준은 "결과 본문에 그 낱말이 실제로 있는가"입니다.

**초안을 사람이 확인하기** — 질문을 AI가 썼다면 그대로 믿지 않습니다. 질문마다 정답과, 근거로 적은 쪽에서 실제로 추출된 본문 발췌를 한 화면에 모아 확인합니다.

```text
요약: {"questions": 22, "k": 5, "hit@1": 0.818, "hit@5": 1.0, "mrr": 0.898, "doc@1": 1.0, "keyword@5": 0.955, "avg_results": 2.14, "precision": 0.735}
```

**파일** `scripts/run-eval.py` · 원본 발췌 · 단위 테스트 8개 통과

```python
def score_question(item, hits, k):
    """검색 결과(hits: document_id·page·text)로 질문 하나를 채점한다."""
    pages = set(item["pages"])
    rank = next((i for i, h in enumerate(hits[:k], 1)
                 if h.get("document_id") == item["document_id"] and h.get("page") in pages), None)
    doc_rank = next((i for i, h in enumerate(hits[:k], 1)
                     if h.get("document_id") == item["document_id"]), None)
    keywords = [w.lower() for w in item.get("keywords") or []]
    keyword_hit = None if not keywords else any(
        w in (h.get("text") or "").lower() for h in hits[:k] for w in keywords)
    shown = hits[:k]
    relevant = sum(1 for h in shown
                   if h.get("document_id") == item["document_id"] and h.get("page") in pages)
    return {"id": item["id"], "status": item["status"], "rank": rank, "doc_rank": doc_rank,
            "returned": len(shown), "relevant": relevant,
            "top1_page": hits[0].get("page") if hits else None,
            "top1_same_doc": bool(hits) and hits[0].get("document_id") == item["document_id"],
            "keyword_hit": keyword_hit}
```

**코드 풀이**

- 정답은 **문서와 쪽이 모두 맞아야** 합니다. 같은 문서의 다른 쪽은 정답이 아닙니다.
- 결과를 저장해 두고 다음 채점 때 순위가 바뀐 질문을 보여 줍니다. 무엇을 고쳤을 때 어떤 질문이 좋아지고 나빠졌는지 바로 보입니다.
- 채점은 검색 단계만 봅니다. 답변 문장은 뒤의 「답변까지 확인하기」에서 따로 확인합니다.

## 문제 1: 채팅이 다른 인덱스를 검색했다

**진단** — 같은 질문을 두 검색 경로에 넣어 비교했습니다.

| 검색 경로 | 검색한 인덱스 | 결과 |
|---|---|---|
| 채팅 RAG 모드 | `langchain_embedding_lab` (실습 문장 3개) | 질문과 무관한 실습 문장 3개, 점수 0.60~0.63 |
| 문서 관리 화면 검색 | `langchain_documents_v1` (업로드 문서) | 1위가 정답 쪽, 점수 0.93 |

벡터 검색은 정상이었고, 채팅이 문장 3개짜리 인덱스에 연결되어 있었습니다.

**파일** `chat_search.py` · 원본 발췌 · 단위 테스트 8개 통과

```python
def search_for_chat(query: str, source: str, *, search_uploaded, search_lab, limit: int = 4) -> list[dict]:
    """설정한 대상에서 검색해 점수 높은 순으로 최대 limit 개를 돌려준다."""
    if source not in SOURCES:
        raise ValueError(f"CHAT_RAG_SOURCE 는 {', '.join(SOURCES)} 중 하나여야 합니다: {source}")
    query = query[:MAX_QUERY]
    found = []
    if source in ("documents", "both"):
        found += [from_uploaded(h) for h in search_uploaded(query, limit=limit)]
    if source == "lab" or source == "both" or (source == "documents" and not found):
        found += [from_lab(h) for h in search_lab(query, limit=min(limit, 3))]
    found.sort(key=lambda h: h["score"] or 0, reverse=True)
    return found[:limit]
```

**코드 풀이**

- `.env`의 `CHAT_RAG_SOURCE`로 대상을 고릅니다. 기본값 `documents`는 업로드 문서를 검색하고, 업로드한 문서가 없을 때만 실습 문장으로 대신합니다.
- `both`는 두 인덱스의 결과를 점수순으로 합칩니다. 두 인덱스 모두 cosine 유사도라 점수를 비교할 수 있습니다.
- 검색 함수를 인자로 받기 때문에 서버 없이 가짜 검색 함수로 테스트할 수 있습니다.
- 근거마다 문서명과 쪽 번호를 답변 모델에 함께 넘깁니다(`[자료 1] (파일명 · p.23) 본문`).

실측 (2026-11-12 20:33, 서버 재시작 후 채팅 RAG 모드):

| 질문 유형 | 근거 1위 | 답변 | 시간 |
|---|---|---|---|
| 핀 연결을 묻는 질문 | 정답 문서의 정답 쪽 (0.93) | 정확 | 16초 |
| 문법 규칙을 묻는 질문 | 정답 문서의 정답 쪽 (0.84) | 정확 | 19초 |
| 숫자 하나를 묻는 질문 | 정답 문서의 정답 쪽 (0.70) | 정확 | 17초 |

외부 API 제공자를 고른 경우에는 제4장의 `ALLOW_EXTERNAL_RAG=false`가 업로드 문서의 내용이 밖으로 나가는 것을 막습니다.

## 문제 2: 관련 없는 쪽이 따라 나왔다

**진단** — 정답 쪽은 1위(0.93)였지만, 2~5위에 같은 문서의 쪽들이 0.86~0.89로 붙어 나왔고 대부분 질문과 관련이 없었습니다. 벡터 검색(kNN)은 "가장 가까운 k개"를 돌려줄 뿐, 관련이 없으면 덜 돌려주는 기능이 없습니다. 질문 하나의 정답 청크는 보통 1~2개인데 항상 5개를 채우니, 나머지 3~4개는 반드시 관련 없는 쪽입니다.

먼저 세운 가설 두 개는 실험에서 **틀린 것으로 나왔습니다.**

| 가설 | 실험 결과 | 판단 |
|---|---|---|
| 쪽마다 반복되는 머리말·꼬리말이 모든 쪽을 비슷하게 만든다 | 머리말을 빼고 다시 임베딩해도 정밀도가 오르지 않음 (0.291 → 0.264) | 기각 |
| 질문에 임베딩 모델용 지시문을 붙이지 않아서다 | 지시문을 붙여도 hit@1 0.818 그대로, 정답과 오답의 점수 차는 오히려 감소 (0.094 → 0.077) | 기각 |

남은 원인은 "항상 5개를 채운다"는 것이었고, 컷오프 폭을 바꿔 가며 쟀습니다.

| 컷오프 폭 | 평균 결과 수 | 정밀도 | 정답 포함 | MRR |
|---|---|---|---|---|
| 없음 | 5.00 | 0.291 | 0.955 | 0.879 |
| 0.05 | 2.64 | 0.674 | 0.955 | 0.879 |
| 0.04 | 2.36 | 0.689 | 0.955 | 0.879 |
| 0.03 | 2.00 | 0.727 | 0.909 | 0.864 |

폭 0.04~0.05까지는 정답을 하나도 잃지 않고 결과가 절반으로 줄었습니다. 0.03부터 정답을 잃기 시작해, 여유를 두고 0.05를 기본값으로 정했습니다.

**파일** `document_pipeline.py` · 원본 · 단위 테스트 3개 통과

```python
def trim_by_margin(hits, margin):
    """(추가) 1위 점수에서 margin 이내인 결과만 남긴다. 순서는 그대로, 1위는 항상 남는다.

    벡터 검색은 관련이 없어도 요청한 개수만큼 채워서 돌려주므로, 같은 문서의 다른 쪽이
    줄줄이 따라 나온다. 평가 세트 22문항(2026-11-12)에서 폭 0.05는 정답을 하나도 잃지 않고
    평균 결과 수를 5 → 2.6개로 줄였다. margin 이 0 이하거나 None 이면 거르지 않는다.
    """
    if not hits or not margin or margin <= 0:
        return list(hits)
    floor = hits[0]["score"] - margin
    return [h for h in hits if h["score"] >= floor]
```

**코드 풀이**

- 1위는 항상 남습니다. 결과가 하나도 없는 화면은 만들지 않습니다.
- 검색 함수 자체는 그대로 두고 결과만 거릅니다. 채점 도구가 `--margin 0`으로 원래 순위를 볼 수 있어야 하기 때문입니다.
- 문서 검색 화면은 숨긴 개수를 알려 줍니다("관련도가 낮은 결과 2개는 숨겼습니다").

## 문제 3: 한 단어 검색에서 엉뚱한 쪽이 나왔다

**진단** — 한 단어로 검색했을 때의 실제 순위를 상위 10개까지 뽑았습니다.

| 벡터 순위 | 청크 | 검색어가 본문에 있는가 |
|---|---|---|
| 1위 | 맞는 문서, 관련 쪽 | 없음 |
| 2위 | **다른 문서**의 61자짜리 표 조각 | 없음 |
| 3위 | 맞는 문서, 관련 쪽 | 없음 |
| 4·5·6·10위 | 맞는 문서 | **있음** |

검색어가 실제로 들어 있는 청크는 5개였는데 모두 4위 이하로 밀렸습니다. 한 단어처럼 짧은 검색어에서는 벡터 유사도가 뜻을 잘 구분하지 못하고, 짧은 조각이 실제보다 높은 점수를 받습니다.

**해결** — 벡터 점수에 "질문 낱말이 본문에 실제로 들어 있는 정도"를 더해 순위를 다시 매깁니다.

**파일** `document_pipeline.py` · 원본 발췌 · 단위 테스트 14개 통과

```python
def query_terms(query):
    """검색에 쓸 낱말 목록 (2글자 이상, 의문 표현 제외, 중복 제거)."""
    out = []
    # 영문·숫자와 한글을 따로 끊는다: 'QRS는' → 'QRS' (+ 1글자 '는' 은 버림), 'K700의' → 'K700'
    for word in re.findall(r"[0-9A-Za-z_]+|[가-힣]+", query):
        if len(word) >= 2 and word not in _QUESTION_WORDS and word not in out:
            out.append(word)
    return out


def term_credits(query, text):
    """질문 낱말별 일치 점수: 그대로 있으면 1.0, 조사를 떼야 있으면 STEM_CREDIT, 없으면 빠짐."""
    flat = re.sub(r"\s+", "", text).lower()
    credits = {}
    for term in query_terms(query):
        forms = _term_forms(term)
        if forms[0] in flat:
            credits[term] = 1.0
        elif any(f in flat for f in forms[1:]):
            credits[term] = STEM_CREDIT
    return credits


def rerank_by_terms(hits, query, weight):
    """벡터 점수에 (일치 낱말 비율 × weight)를 더해 다시 정렬한다. hits 의 score 는 벡터 점수."""
    terms = query_terms(query)
    out = []
    for hit in hits:
        credits = term_credits(query, hit.get("text", "")) if terms else {}
        found = list(credits)
        coverage = sum(credits.values()) / len(terms) if terms else 0.0
        bonus = (weight or 0) * coverage
        out.append({**hit, "vector_score": hit["score"], "term_coverage": round(coverage, 3),
                    "matched_terms": found,
                    # (추가) 조사를 떼야만 일치한 낱말 — 화면에서 '일부 일치'로 구분해 보여 준다
                    "partial_terms": [t for t, c in credits.items() if c < 1.0],
                    "score": round(hit["score"] + bonus, 4),
                    "snippet": make_snippet(hit.get("text", ""), found)})
    out.sort(key=lambda h: -h["score"])
    return out
```

**코드 풀이**

- 낱말은 영문·숫자와 한글을 따로 끊습니다. `K700의`는 `K700`이 되고, 1글자 조사는 버립니다.
- 본문과 비교할 때는 띄어쓰기와 대소문자를 무시합니다. PDF에서 뽑은 글은 글자 사이에 공백이 끼어 있는 일이 많기 때문입니다.
- **낱말이 그대로 있으면 1점, 조사를 떼야 일치하면 0.5점**입니다. 처음에는 둘을 같은 점수로 쳤다가, `산업안전`을 검색했는데 `산업`만 있는 쪽이 `산업안전`이 있는 쪽을 가리는 문제가 생겨 나눴습니다.
- 조사 처리는 한글 낱말의 뒤 1~2글자를 떼어 보는 단순한 규칙입니다. 형태소 분석기만큼 정확하지 않습니다.
- `SEARCH_TERM_WEIGHT=0`이면 재순위가 꺼지고 이전과 똑같은 순위가 됩니다.

가중치를 바꿔 가며 잰 결과 (문서 5개):

| 설정 (부분 점수 / 가중치) | 질문 hit@1 | MRR | 정답 포함 | 한 단어: 낱말 포함률 | 한 단어: 1위에 낱말 |
|---|---|---|---|---|---|
| 재순위 없음 | 0.818 | 0.879 | 0.955 | 0.475 | 0.583 |
| 1.0 / 0.10 | 0.864 | 0.924 | 1.000 | 0.889 | 0.917 |
| **0.5 / 0.15 (채택)** | 0.818 | 0.890 | 1.000 | **0.983** | **1.000** |

**상충 관계** — 채택한 설정은 한 단어 검색을 우선한 것입니다. 자연어 질문만 보면 `1.0 / 0.10`이 hit@1에서 앞서지만, 그 설정에서는 부분 일치가 정확한 일치를 가렸습니다. 채택한 설정에서는 질문 하나의 정답이 1위에서 3위로 내려갔고, 정답이 결과에 포함되는 비율은 22문항 모두 유지됐습니다.

화면 표시도 함께 바꿨습니다. 쪽 전체 대신 검색어가 처음 나오는 곳 주변 약 260자를 먼저 보여 주고, 전체는 펼쳐 보게 했습니다. 점수는 "벡터 점수 + 낱말 점수"로 나눠 보여 주고, 조사를 떼야만 일치한 낱말은 "(일부만 일치)"로 표시합니다.

## 문제 4: 문서가 늘면 후보에서 빠졌다

**진단** — 문서를 12개(732청크)로 늘려 검증하자 한 단어 검색의 낱말 포함률이 0.750으로 떨어졌습니다. 재순위는 벡터 검색이 뽑은 후보 30개 안에서만 순서를 바꾸는데, 검색어가 든 청크의 벡터 순위가 32위·121위였습니다. 후보에 못 들어오면 끌어올릴 수 없습니다. 문서 5개(138청크)일 때는 보이지 않던 문제입니다.

**해결** — 벡터 후보와 별도로, 질문 낱말이 든 청크를 Elasticsearch에서 직접 찾아 후보에 합칩니다.

**파일** `document_pipeline.py` · 원본 발췌 · 단위 테스트 7개 통과

```python
def lexical_candidates_query(query, document_id=None):
    """(추가) 질문 낱말이 본문에 들어 있는 청크를 찾는 Elasticsearch 질의. 낱말이 없으면 None.

    벡터 후보 30개만 보면, 문서가 늘었을 때 낱말이 든 청크가 후보에 못 들어온다
    (실측: 732청크에서 검색어가 든 청크의 벡터 순위가 32위·121위). 그래서 낱말로도 후보를 찾는다.
    낱말은 영문·숫자·밑줄·한글뿐이라 wildcard 특수문자(* ? \\)가 들어갈 수 없다.
    일치한 낱말 수가 많은 청크가 먼저 온다(낱말마다 점수 1).
    """
    terms = query_terms(query)[:LEXICAL_TERMS_MAX]
    if not terms:
        return None
    should = [{"constant_score": {"boost": 1.0, "filter": {"bool": {"should": [
        {"wildcard": {"text": {"value": f"*{form}*", "case_insensitive": True}}}
        for form in _term_forms(term)]}}}} for term in terms]
    body = {"bool": {"should": should, "minimum_should_match": 1}}
    if document_id:
        body["bool"]["filter"] = [{"term": {"document_id": document_id}}]
    return body


def cosine_score(query_vector, embedding):
    """Elasticsearch 의 cosine kNN 점수와 같은 값: (1 + 코사인 유사도) / 2."""
    dot = sum(a * b for a, b in zip(query_vector, embedding))
    norm = (sum(a * a for a in query_vector) ** 0.5) * (sum(b * b for b in embedding) ** 0.5)
    return round((1 + dot / norm) / 2, 4) if norm else 0.0


def merge_candidates(vector_hits, lexical_hits):
    """벡터 후보에 낱말 후보를 더한다. 같은 청크(문서 ID + 청크 ID)는 한 번만, 벡터 후보가 우선."""
    seen = {(h.get("document_id"), h.get("chunk_id")) for h in vector_hits}
    merged = list(vector_hits)
    for hit in lexical_hits:
        key = (hit.get("document_id"), hit.get("chunk_id"))
        if key not in seen:
            seen.add(key)
            merged.append(hit)
    return merged
```

**코드 풀이**

- 낱말 후보에는 벡터 검색 점수가 없으므로, 저장된 벡터로 같은 공식 `(1 + 코사인 유사도) / 2`를 직접 계산합니다.
- 같은 청크인지는 **문서 ID와 청크 ID를 함께** 비교합니다. 청크 ID(`s0001_c001`)는 문서마다 같은 값이 반복됩니다. 이것을 모르고 청크 ID만으로 합친 실험이 엉뚱한 수치를 낸 적이 있어 테스트로 고정했습니다.
- 낱말은 영문·숫자·밑줄·한글뿐이라 wildcard 특수문자가 들어갈 수 없습니다(테스트로 확인).
- 검색 한 번의 시간은 1,176청크에서 중앙값 0.09초, 최대 0.13초였습니다.

## 답변까지 확인하기

여기까지의 채점은 **검색 단계**만 봅니다. 정답 쪽을 찾았어도 채팅이 그 내용을 맞게 말하는지는 따로 확인해야 합니다. 평가 질문을 실제 채팅(RAG 모드)에 넣고 답변을 기계적으로 확인하는 도구를 만들었습니다.

질문 파일의 각 줄에 `answer_keys`를 더합니다 (내용은 지어낸 예시).

```json
{"id": "q01", "question": "실습 장비는 몇 대 필요해?", "document_id": "a1b2c3", "pages": [4, 12], "answer_keys": [["3대", "3 대"], ["12,340"]]}
```

- 바깥 목록의 **모든 묶음**이 답변에 있어야 합니다. 묶음 안에서는 하나만 있으면 됩니다(표기가 여러 가지일 때).
- 띄어쓰기와 대소문자는 무시합니다.

```bash
# 전체 확인 (질문당 15~20초, 문서·색인을 바꾸지 않음, 답변 본문은 출력하지 않음)
cd ~/langchain_web
.venv/bin/python scripts/run-answer-eval.py

# 앞의 3문항만
.venv/bin/python scripts/run-answer-eval.py --limit 3
```

| 확인 항목 | 뜻 |
|---|---|
| 근거 포함 | 채팅이 근거로 쓴 자료에 정답 문서의 정답 쪽이 있는가 |
| 사실 포함 | 답변에 `answer_keys`가 들어 있는가 |
| 인용 | 답변에 `[자료 1]` 같은 출처 표시가 있는가 |
| 대체 문구 | 한국어 답변을 만들지 못해 안내 문구로 바뀌었는가 |
| 외국 문자 | 답변에 한자·가나·태국 문자 등이 몇 자 섞였는가 |
| 처리 결과 | 서버가 답을 교정했는가 (`none` · `light` · `kept` · `heavy` · `fallback`). `kept`는 고치지 못해 원래 답을 그대로 보냈다는 뜻이고, 한국어가 대부분인 답이면 안내 문구로 바꾸지 않고 이 값이 됩니다 |
| 근거 밖 | 답의 숫자·영문 중 근거 자료에서 못 찾은 것의 개수 (문제 7). 사람이 볼 후보이지 판정이 아닙니다 |
| 인용 오류 | 근거 개수를 넘는 번호(없는 자료)를 인용한 답의 수 (문제 8) |

실측 (2026-11-12 23:38, 초안 22문항, 아래 문제 5의 교정을 넣기 전, 요약 줄만):

```text
요약: {"questions": 22, "evidence": 1.0, "facts": 0.955, "facts_checked": 22, "cited": 0.5, "fallback": 0, "seconds_median": 14.2, "seconds_max": 51.9}
```

- 근거는 22문항 모두 맞게 전달됐고, 핵심 사실은 21문항의 답변에 들어 있었습니다.
- 출처 표시는 절반(11문항)에만 있었습니다. 지시문에 자료 번호를 표시하라고 적어도 지켜지지 않는 경우가 많습니다.

**이 도구가 잡지 못하는 것** — 저장된 답변을 직접 읽어 보니 숫자로는 보이지 않는 문제가 있었습니다.

| 직접 읽어 확인한 문제 | 답변 수 | 도구가 잡는가 |
|---|---|---|
| 외국 문자가 섞임 (한자 1자, 일본어 가나, 태국 문자) | 4 | 처음에는 못 잡음 → "외국 문자" 항목을 추가 |
| 약어의 뜻을 지어냄 (문서에 없는 풀이) | 2 | 못 잡음 |
| 사실이 틀림 | 1 | 잡음 (사실 포함 = 아니오) |

`사실 포함`은 **핵심 낱말이 답변에 있는지**만 봅니다. 틀린 설명 속에 맞는 숫자가 들어 있어도 통과합니다. 답변 전체가 옳은지는 사람이 읽어야 합니다. 답변 본문에는 내 문서의 내용이 들어 있으므로 `data/eval/answer-results/`에만 저장하고 화면에는 출력하지 않습니다.

## 문제 5: 답변에 외국 문자가 섞였다

**진단** — 로컬 모델은 한국어 답변에 가끔 다른 문자를 섞습니다. 서버에는 이미 검사가 있었지만 **한자가 2자 이상**일 때만 다시 쓰게 했습니다. 그래서 `답案`(한국어 낱말 속 한자 1자), `に関わる`(일본어 가나), 태국 문자는 그대로 나갔습니다(22문항 중 4문항).

**처음 만든 방법과 버린 이유** — 모델에게 답을 다시 쓰게 하고, 외국 문자가 줄었고 숫자·영문 이름이 남아 있으면 **다시 쓴 글 전체를 채택**하는 방법을 먼저 만들었습니다. 서버에 넣기 전에 다시 쓰기 단계만 따로 쟀습니다.

```text
저장해 둔 답변 22개
  ├─ 실제로 외국 문자가 섞였던 답 4개 ── 그대로 사용
  └─ 깨끗한 답 17개 ── 한국어 낱말 하나에 한자·가나를 한 글자 넣음 (예: 방법 → 方법)
        ↓  모델에게 다시 쓰게 함 (21개, 문서·색인·서버는 바꾸지 않음)
  (초안, 다시 쓴 글)을 파일로 저장 → 채택 조건을 바꿔 가며 모델 호출 없이 다시 계산
```

다시 쓴 글을 초안과 비교하니, 모델은 외국 문자만 고치지 않았습니다. 지시문을 "외국 문자가 든 낱말만 고치라"로 바꿔도 마찬가지였습니다.

| 모델이 함께 바꾼 것 | 결과 |
|---|---|
| 외국 문자와 상관없는 전문 용어를 답 전체에서 다른 말로 바꿈 | 숫자·영문이 그대로라 조건을 통과 → 핵심 낱말을 잃음 (21개 중 1개) |
| `[자료 1]`의 대괄호를 지움, 영문 이름을 한글로 옮김 | 조건에 걸려 원래 답 유지 (교정 실패) |
| 되풀이된 요약을 합쳐 글이 절반 가까이 줄어듦 | 조건에 걸려 원래 답 유지 (교정 실패) |

조건을 하나씩 더 붙이는 방식으로는 끝이 없습니다. **다시 쓴 글 전체를 받는 한, 바뀔 수 있는 모든 것을 검사해야 합니다.**

**해결** — 다시 쓴 글을 원래 답과 글자 단위로 비교해, **외국 문자가 있던 자리의 수정만** 원래 답에 옮깁니다. 그 밖의 변경은 모두 버립니다.

```text
원래 답    : 절차는 結과를 [자료 1]에 따라 sum_bits 로 냅니다.
다시 쓴 글 : 작업은 결과를 자료 1에 따라 비트합 로 냅니다.
               ↓ 글자 단위 비교
바뀐 자리  : 절차→작업 (버림)   結→결 (옮김)   [ ] 삭제 (버림)   sum_bits→비트합 (버림)
               ↓
보내는 답  : 절차는 결과를 [자료 1]에 따라 sum_bits 로 냅니다.
```

**파일** `app.py` · 원본 발췌 · 단위 테스트 31개 통과 (`tests/test_korean_rewrite.py`)

```python
def _fixed_marks(text: str, allowed: str) -> list[str]:
    """한 자리에서 그대로 남아야 하는 글자: 숫자·영문·기호. (한글·공백·섞인 외국 문자·깨진 글자는 바뀔 수 있다)"""
    stray = set(stray_characters(text, allowed))
    return [ch for ch in text if not ("가" <= ch <= "힣" or ch.isspace() or ch in stray or ch == "\ufffd")]


def _is_leak_fix(old: str, new: str, allowed: str) -> bool:
    """다시 쓴 글의 한 자리 수정(old → new)을 원래 답에 옮겨도 되는지."""
    if not stray_characters(old, allowed):
        return False                                   # 이 자리에는 외국 문자가 없었다 → 상관없는 수정
    if len(old) > LEAK_SPAN_MAX or len(new) > len(old) + LEAK_GROWTH_MAX:
        return False                                   # 주변 문장까지 바꿨거나 낱말을 덧붙였다
    if stray_characters(new, allowed):
        return False                                   # 다른 외국 문자로 바꿨다
    if _fixed_marks(old, allowed) != _fixed_marks(new, allowed):
        return False                                   # 숫자·영문·기호(**, [ ], - 등)가 달라졌다
    hangul = re.compile("[가-힣]")
    return len(hangul.findall(new)) >= len(hangul.findall(old))   # 그 자리에 있던 한글을 지웠으면 받지 않는다


def merge_leak_fixes(original: str, rewrite: str, allowed: str = "") -> str:
    """다시 쓴 글에서 '외국 문자가 있던 자리'의 수정만 원래 답에 옮긴다. 그 밖의 변경은 모두 버린다."""
    parts = []
    matcher = difflib.SequenceMatcher(None, original, rewrite, autojunk=False)
    for tag, i1, i2, j1, j2 in matcher.get_opcodes():
        old, new = original[i1:i2], rewrite[j1:j2]
        parts.append(new if tag != "equal" and _is_leak_fix(old, new, allowed) else old)
    return "".join(parts)
```

**코드 풀이**

- `difflib.SequenceMatcher`는 두 글을 같은 구간과 다른 구간으로 나눕니다. 다른 구간마다 "이 자리에 외국 문자가 있었는가"를 보고, 있었던 자리만 새 글자로 바꿉니다.
- 자리 하나에도 조건이 있습니다. 12자 이내일 것, 4자 넘게 늘지 않을 것, 숫자·영문·기호가 그대로일 것, 그 자리에 있던 한글을 지우지 않을 것, 다른 외국 문자로 바꾸지 않을 것.
- 사용자가 쓴 글과 참고 문서에 있는 글자는 인용일 수 있으므로 외국 문자로 세지 않습니다. 질문이 번역이나 외국어 표기를 요청한 대화에서는 교정하지 않습니다.
- 고치지 못하면 원래 답을 그대로 보냅니다. 맞는 답을 안내 문구로 바꾸지 않습니다.
- 글자 단위 비교는 글이 길수록 느립니다(절반을 다시 쓴 글과 비교한 실측: 1,000자 0.07초, 3,000자 1.2초, 6,000자 7.3초). 그래서 3,000자를 넘는 답은 손대지 않습니다.
- 한자가 2자 이상 섞인 답은 이전과 같이 전체를 다시 쓰게 하고, 그래도 안 되면 안내 문구로 바꿉니다. 이 경로는 바꾸지 않았습니다.
- `.env`의 `CHAT_LIGHT_LEAK_FIX=false`로 끌 수 있습니다. 끄면 이전처럼 답을 그대로 보냅니다. 섞인 답만 모델 호출이 한 번 늘어 10~20초 늦어집니다.

**지시문 비교** — 같은 초안 21개. 모델 출력을 저장해 두고 실제 코드에 넣어 계산했습니다.

| 다시 쓰게 할 때의 지시문 | 외국 문자가 없어진 답 | 핵심 낱말을 잃은 답 | 판정 |
|---|---|---|---|
| 기존: "자연스러운 한국어로 재작성" | 14 / 21 | 0 | 문장을 합치거나 바꿔, 옮길 자리를 찾지 못하는 일이 많음 |
| "외국 문자가 든 낱말만 바꾸고 나머지는 그대로" | 16 / 21 | 0 | **채택.** 21개 답에서 바뀐 글자는 모두 합쳐 27자 |
| 섞인 글자를 알려 주고 "한자는 독음으로" | 18 / 21 | 0 | 기각. 틀린 음으로 바꾼 것이 있음 (사용 → 시용) |

**실제 채팅으로 다시 확인** (2026-11-13 00:19, 서버 반영 후 같은 22문항, 요약 줄만):

```text
요약: {"questions": 22, "evidence": 1.0, "facts": 0.909, "facts_checked": 22, "cited": 0.455, "fallback": 1, "foreign_answers": 0, "rewritten": 1, "seconds_median": 14.4, "seconds_max": 42.3}
```

이 결과를 "외국 문자가 섞인 답이 4개에서 0개로 줄었다"고 읽으면 안 됩니다.

- 이번 실행에서는 가벼운 혼입이 **한 건도 생기지 않았습니다.** 새 교정은 실행될 기회가 없었습니다(`rewritten` 1건은 아래의 안내 문구 대체입니다).
- 같은 질문인데 답이 달라졌습니다. 모델에 보내는 지시문에 오늘 날짜가 들어가는데 그 사이 날짜가 바뀌었고, 같은 입력에도 답이 조금씩 달라집니다. **한 번 잰 수치의 차이를 고친 효과로 단정하지 않습니다.**
- 한 문항은 이번에 한자가 2자 이상 섞여 기존 경로로 들어갔고, 다시 써도 고쳐지지 않아 안내 문구로 바뀌었습니다. 그래서 사실 포함이 21 → 20문항이 됐습니다. 이 경로는 이번에 바꾸지 않은 기존 동작입니다.

그래서 새 교정이 실제 경로에서 동작하는지는 따로 확인했습니다. 전날 실제로 외국 문자가 섞였던 답 4개를 첫 답으로 넣고, 그 뒤(실제 검색 → 실제 모델에게 교정 요청 → 자리별 수정)는 서버 코드를 그대로 실행했습니다(2026-11-13 00:25).

| 섞였던 것 | 처리 결과 | 외국 문자 | 핵심 낱말 | 답변 길이 |
|---|---|---|---|---|
| 태국 문자 (깨진 글자 포함) | `light` (교정) | 4 → 0 | 유지 | 435 → 432자 |
| 한국어 낱말 속 한자 1자 | `kept` (원래 답 유지) | 1 → 1 | 유지 | 331 → 331자 |
| 한국어 낱말 속 한자 1자 | `kept` (원래 답 유지) | 1 → 1 | 유지 | 131 → 131자 |
| 일본어 가나 | `kept` (원래 답 유지) | 4 → 4 | 변화 없음 | 830 → 830자 |

실제 경로에서는 4개 중 1개만 고쳐졌습니다. 저장해 둔 모델 출력으로 계산했을 때는 가나가 섞인 답도 고쳐졌지만(4개 중 2개), 이번에는 모델이 다르게 고쳐 써서 자리별 조건을 통과하지 못했습니다. 고치지 못한 답은 한 글자도 바뀌지 않았습니다. **효과는 작고, 대신 답을 망가뜨리지 않습니다.**

**남은 한계** — 한국어 낱말 속에 한자가 한 글자 섞인 답(4개 중 2개)은 모델이 그 글자를 고치지 않아 그대로 남습니다. 이 꼴은 한자 음 표로 바꾸면 정확하고 모델을 부를 필요도 없습니다(**아래 문제 6에서 해결했습니다**). 확인한 패키지(`hanja` 0.15.1)는 설치할 때 이미 쓰고 있는 PyYAML을 낮은 버전으로 바꾸고 시험 도구 3개를 함께 요구해 설치하지 않았습니다(2026-11-13, 내려받아 설치 정보만 확인).

## 같은 질문을 여러 번 재기

같은 질문을 같은 모델에 두 번 던져도 답이 같지 않습니다. 평가 도구로 15문항을 두 번 돌렸더니, 한 질문은 첫 번째에 깨끗했고 두 번째에는 외국 문자가 8자 섞였습니다. 이런 흔들림 때문에 **한 번 잰 수치의 차이로는 무엇을 고쳤는지 판단할 수 없습니다.**

```bash
# 전체를 3번 돌려 평균과 최소~최대를 본다 (문서·색인은 바꾸지 않음)
.venv/bin/python scripts/run-answer-eval.py --repeat 3
```

**파일** `scripts/run-answer-eval.py` · 원본 발췌

```python
AGGREGATE_KEYS = ("evidence", "facts", "cited", "bad_cite_answers", "ungrounded_answers", "fallback", "foreign_answers", "rewritten")


def aggregate(summaries: list[dict]) -> dict:
    """여러 번 돌린 요약에서 항목별 평균·최소·최대. 값이 없는(None) 실행은 뺀다."""
    out = {"runs": len(summaries)}
    for key in AGGREGATE_KEYS:
        values = [s[key] for s in summaries if s.get(key) is not None]
        if values:
            out[key] = {"mean": round(statistics.mean(values), 3), "min": min(values), "max": max(values)}
    return out
```

- 값이 없는 실행(`None`)은 0으로 세지 않고 뺍니다. 0으로 세면 평균이 낮아집니다.
- **판단 기준**: 변경 전과 후의 최소~최대 범위가 겹치면 그 차이를 효과로 보지 않습니다. 범위가 겹치지 않으면 효과로 봅니다. 이 장의 뒤쪽 비교는 모두 이 기준으로 읽습니다.
- 서버를 두 개 띄워(실제 서버와 임시 서버) 같은 질문을 동시에 돌리면 변경 전후를 같은 조건에서 볼 수 있습니다. 다만 **메모리를 많이 씁니다.** 아래 "운영 중 메모리 부족" 절(5장)처럼 서비스가 죽을 수 있어, 한 번에 하나만 돌립니다.
- 서버가 도중에 죽으면 수치가 무효가 됩니다. 자동 모드 평가에서 검색이 실패해 일반 대화로 답한 경우를 `search_failed`로 세고, 있으면 "수치를 믿을 수 없다"는 경고를 출력합니다.

## 문제 6: 한자 한 글자가 섞인 답 — 한자 음 표

**진단** — 위 문제 5의 "남은 한계"에 적은 대로, `답案`처럼 한국어 낱말 속에 한자가 한 글자 섞인 답은 모델이 고치지 못했습니다. 이 꼴은 한자 음 표로 바꾸면 모델을 부르지 않고 정확하게 고칠 수 있습니다.

**표 만들기** — 유니코드가 공개한 한자 자료(Unihan)의 `kHangul`(한글 음)로 만듭니다. 이 자료는 `https://www.unicode.org/Public/UCD/latest/ucd/Unihan.zip`에서 내려받는 공개 파일이라 개인 정보를 보낼 일이 없고, 설치한 패키지도 없습니다. 라이선스는 Unicode License v3입니다.

```bash
# 내려받은 Unihan_Readings.txt 경로를 넘긴다 → static_data/hanja_ko.json (8,349자)
.venv/bin/python scripts/build-hanja-table.py <Unihan_Readings.txt 경로>
```

**처음 만든 기준이 틀렸다** — 음이 여러 개인 글자는 "표준 음 표시(`E`)가 정확히 하나면 그것을 고른다"로 정했습니다. 시험에서 `樂器`가 `낙기`로 바뀌었습니다(실제는 악기). `樂`은 낙·락·악·요를 모두 읽는 글자인데, 표준 표시가 붙은 음이 우연히 하나였습니다. 기준을 바꿨습니다.

| 글자의 음 | 표에 넣는가 | 예 |
|---|---|---|
| 음이 하나뿐 | 넣음 | 案 → 안 |
| 음이 여럿이지만 두음법칙 차이뿐 | 넣음 (본음으로) | 力: 력·역 → 력 |
| 음이 정말 여럿 | **넣지 않음** (176자) | 樂 · 行 · 說 |

표에 없는 글자는 바꾸지 않고 그대로 둡니다. 틀리게 바꾸느니 남깁니다. 이 수정에 쓴 사례(`樂`, `規律`)는 증거로 세지 않고, 따로 고른 낱말 10개(學校·電子·回路·電壓 등)로 다시 확인했습니다.

**규칙** — 낱말 첫머리에서만 두음법칙을 적용하고, 한글 뒤에 붙은 한자는 본음을 씁니다.

| 입력 | 결과 | 이유 |
|---|---|---|
| `답案을 쓰세요` | `답안을 쓰세요` | 한글 뒤 → 본음 |
| `力學과 論理` | `역학과 논리` | 낱말 첫머리 → 두음법칙 |
| `規律` · `序列` | `규율` · `서열` | 모음·ㄴ 뒤의 렬·률은 열·율 |
| `法律` | `법률` | 그 밖의 받침 뒤는 본음 |
| `樂器` | `樂기` | 표에 없는 글자는 그대로 |

**파일** `hanja_ko.py` · 원본 발췌

```python
def initial_sound_law(syllable: str) -> str:
    """낱말 첫머리의 한글 음절에 두음법칙을 적용한다 (녀→여, 력→역, 론→논 …)."""
    code = ord(syllable) - 0xAC00
    initial, rest = divmod(code, 21 * 28)
    medial, final = divmod(rest, 28)
    if initial == _INITIAL_N and medial in _I_LIKE:
        initial = _INITIAL_IEUNG
    elif initial == _INITIAL_R:
        initial = _INITIAL_IEUNG if medial in _I_LIKE else _INITIAL_N
    else:
        return syllable
    return chr(0xAC00 + (initial * 21 + medial) * 28 + final)
```

- 한글 음절은 `(첫소리 × 21 + 가운뎃소리) × 28 + 받침 + 0xAC00`으로 만들어집니다. 나눗셈으로 세 부분을 꺼내 첫소리가 ㄴ·ㄹ일 때만 바꿉니다.
- 질문이나 참고 문서에 있던 글자는 인용일 수 있으므로 바꾸지 않습니다.
- 한계: 앞 낱말이 접두어인 경우(신女性 → 신여성) 같은 맞춤법 예외와, 문맥에 따라 읽기가 달라지는 글자는 다루지 못합니다.

**거의 중국어인 답에는 쓰지 않는다** — 처음에는 모든 답에 표를 썼습니다. 모델이 거의 중국어로 답한 경우에도 표가 `这是中文回答`을 `这시중문회答`처럼 한글과 한자가 뒤섞인 글로 만들었습니다. 표는 **한글이 섞인 외국 문자의 2배 이상인 답**에만 씁니다(`korean_dominant`).

### 안내 문구를 줄이기 — 새 처리 순서

사용자 결정(2026-11-13)에 따라, 한국어가 대부분인 답에 한자가 조금 섞였을 때 **답 전체를 안내 문구로 바꾸지 않습니다.**

```text

② 그래도 한자가 2자 이상 남으면 모델이 한 번 다시 씀 (이전과 같음)
③ 그래도 안 되면
     한국어가 대부분인 답 → 원래 답을 그대로 보여 줌   (처리 결과 kept)
     거의 외국어인 답     → 안내 문구로 바꿈             (처리 결과 fallback)
```

"한국어가 대부분"의 기준은 **한글이 20자 이상이고 섞인 외국 문자의 10배 이상**입니다(`mostly_korean`).

**파일** `app.py` · 원본 발췌

```python
def polish_answer(answer: str, asked: str, allowed: str, invoke_rewrite) -> dict:
    result = {"answer": answer, "state": "none", "hanja_fixed": 0, "draft": None}
    asks_foreign = asks_foreign_text(asked)   # 외국어 표기를 요청한 대화: 표·가벼운 교정은 하지 않는다
    original = answer                          # 모델이 낸 그대로 (기록용)
    if settings.CHAT_HANJA_TABLE and not asks_foreign and korean_dominant(answer, allowed):
        answer, fixed, _ = hanja_ko.to_hangul(answer, allowed)
        result.update(answer=answer, hanja_fixed=fixed)
    if needs_korean_rewrite(answer):
        draft = answer
        rewrite = invoke_rewrite(REWRITE_PROMPT, draft)
        rewrite = rewrite if isinstance(rewrite, str) else str(rewrite)
        if rewrite.strip() and not needs_korean_rewrite(rewrite):
            result.update(answer=rewrite, state="heavy")
        elif settings.CHAT_KEEP_DRAFT_ON_FAIL and mostly_korean(draft, allowed):
            result.update(answer=draft, state="kept", draft=original)      # 안내 문구로 바꾸지 않는다
        else:
            result.update(answer=FALLBACK_NOTICE, state="fallback", draft=original)
    elif settings.CHAT_LIGHT_LEAK_FIX and not asks_foreign:
        fixed_answer, state = fix_light_leak(answer, allowed, lambda prompt, draft: invoke_rewrite(prompt, draft))
        result.update(answer=fixed_answer, state=state)
    return result
```

## 문제 7: 답의 숫자·영문이 근거에 있는가 — 근거 대조

**진단** — 위 "답변까지 확인하기"에서 `사실 포함`은 핵심 낱말만 봅니다. 답에 문서에 없는 영문 풀이나 숫자가 덧붙어도 통과합니다. 사람이 읽어야 한다고만 적어 두었는데, **읽을 후보를 좁혀 주는 도구**는 만들 수 있습니다.

**방법** — 답에 나온 숫자와 영문 낱말(3자 이상)이 근거로 쓴 자료·질문·자료 머리말(파일 이름·제목·쪽)에 실제로 있는지 대조합니다. 모델은 부르지 않습니다.

**파일** `grounding.py` · 원본 발췌

```python
def _has_number(number: str, haystack: str) -> bool:
    """자릿수가 이어지지 않는 위치에서 찾는다 ('8' 이 '18' 안에서 찾아지면 안 된다)."""
    return re.search(r"(?<!\d)(?<!\d\.)" + re.escape(number) + r"(?![\d]|\.\d)", haystack) is not None


def check(answer: str, sources: list[str], question: str = "") -> dict:
    """{'numbers': 근거에서 못 찾은 숫자, 'words': 못 찾은 영문 용어, 'checked': 대조한 개수}"""
    evidence = "\n".join(sources) + "\n" + question
    flat_numbers = evidence.replace(",", "")
    lowered = evidence.lower()
    nums, words = _numbers(answer), _words(answer)
    return {
        "numbers": [n for n in nums if not _has_number(n, flat_numbers)],
        "words": [w for w in words if w not in lowered],
        "checked": len(nums) + len(words),
    }
```

- 쉼표는 무시하고(`1,200` = `1200`), 줄 머리의 목록 번호와 `[자료 N]` 표시는 뺍니다.
- 질문에 이미 있는 값은 사용자가 준 것이므로 근거로 인정합니다.
- 평가 도구에는 "근거 밖" 항목으로 개수만 출력하고, 걸린 항목의 목록은 저장 파일에만 남깁니다. 답 본문이 섞일 수 있어서입니다. 근거 자료가 없는 답(라이브러리가 직접 답한 경우 등)은 대조하지 않습니다.

**처음 실행에서 찾은 오탐 2가지**

| 오탐 | 원인 | 고침 |
|---|---|---|
| 답이 출처 표시에 적은 파일 이름·쪽 번호가 걸림 | 자료 머리말은 모델이 받은 정보인데 근거로 안 셈 | 파일 이름·제목·쪽을 근거로 인정 |
| `p.8`의 `8`을 못 찾음 | 소수점 보호 규칙(`3.85`의 `5`를 막으려는)이 점 뒤의 숫자를 모두 막음 | **숫자 뒤의 점**일 때만 막도록 좁힘 |

**실제 모델 답으로 확인** (2026-11-14, 14개 답): 4개 답에서 걸렸고, 사람이 읽어 분류했습니다.

| 분류 | 개수 | 뜻 |
|---|---|---|
| 계산한 값 | 2 | 근거의 두 숫자를 빼거나 비율로 계산한 결과. **계산은 옳았지만** 근거에 그 숫자가 없어 걸림 |
| 문서에 없는 일반 지식을 덧붙임 | 2 | 이 도구가 찾으려던 종류 |

**한계** — 이 도구는 판정이 아니라 "사람이 볼 후보 목록"입니다.

- 계산한 값은 걸립니다(원리상 피할 수 없습니다).
- 근거에 있는 숫자를 **엉뚱한 곳에** 쓴 틀린 답은 걸러내지 못합니다. 이 한계는 단위 테스트에 명시해 두었습니다.
- 영문 약어나 표기 차이도 걸릴 수 있습니다. 표본이 14개 답이라 걸리는 비율은 참고만 합니다.

## 문제 8: 출처 표시 — 지시문을 바꿔 보고 기각했다

**진단** — 답에 `[자료 1]` 같은 표시가 붙는 비율이 절반 아래였습니다(같은 조건 3번 측정: 평균 0.386, 범위 0.333~0.467). 화면에는 답 아래에 근거 목록이 항상 나오므로 출처를 알 수 있기는 합니다. 그런데 목록의 번호는 `[1]` 형식이고 답의 표시는 `[자료 1]` 형식이라 서로 대응하지 않았습니다. **목록 번호를 `[자료 1]`로 맞췄습니다.**

**지시문 실험** — 지시문을 더 분명하게 바꾸면 비율이 오르는지 같은 15문항 × 3번으로 쟀습니다(2026-11-14). 지시문은 환경 변수 `RAG_CITE_PROMPT`로 바꿀 수 있게 분리했고, 기본값은 기존 문구 그대로입니다.

| 지시문 | 인용이 붙은 답 | 정답 단어 포함 | 판정 |
|---|---|---|---|
| 기준: "사용한 자료 번호를 표시하세요" | 0.386 (0.333~0.467) | 0.932 (0.929~0.933) | — |
| 1: "각 문장 끝에 근거 번호를 반드시 붙이세요" | 0.933 | 0.822 (0.80~0.867) | **기각** |
| 2: 1 + "내용을 빠짐없이, 번호를 붙이느라 줄이지 마세요" | 0.889 (0.867~0.933) | 0.867 (3번 모두 같음) | **기각** |

- 두 지시문 모두 인용은 범위가 겹치지 않을 만큼 확실히 올랐습니다. 그런데 정답 포함도 범위가 겹치지 않게 **내려갔습니다.**
- 지시문 1에서는 한 질문의 답이 3번 모두 66자로 짧아졌습니다(기준에서는 400자대). 번호를 붙이는 데 신경 쓰다 내용이 줄어든 것으로 보입니다(길이만 확인한 추정입니다).
- 지시문 2는 그 질문을 회복했지만 다른 질문에서 정답 묶음이 실행마다 다르게 빠졌습니다. 15문항 중 1문항 차이입니다.
- 정확도가 우선이어서 **지시문 기본값은 바꾸지 않았습니다.** 대신 아래의 "코드로 출처를 붙이기"를 채택했습니다.

**코드로 출처를 붙이기 (채택)** — 지시문을 바꾸지 않고, 답이 끝난 뒤 **코드가 출처를 붙입니다**(`answer_cite.py`, 모델 호출 없음). 답과 글이 가장 많이 겹치는 근거를 찾아 답 끝에 "근거: [자료 N] (문서 · p.N)" 줄을 붙입니다. 모델이 이미 유효한 `[자료 N]`을 썼으면 그대로 두고, 없는 번호는 지웁니다. 겹치는 근거가 하나도 없으면 아무것도 붙이지 않습니다(근거 없는 출처를 지어내지 않음). 겹침 기준(글자 4개 묶음의 일치율, 최대 2개)은 결과를 보기 전에 정했고 평가에 맞춰 조정하지 않았습니다. 끄려면 `CHAT_AUTO_CITE=false`.

| 측정 | 기준 | 코드 부착 후 |
|---|---|---|
| 정답 쪽을 가리키는 비율 (다른 작업 세션이 개발용·보류용 질문으로 따로 측정) | 0.47~0.49 | 0.85~0.97 |
| 인용이 붙은 답 (이 장의 평가 도구, 15문항 × 3번) | 0.386 (0.333~0.467) | **0.978 (0.933~1.0)** |
| 정답 단어 포함 (같은 실행) | 0.932 (0.929~0.933) | 0.955 (0.933~1.0), 악화 없음 |
| 잘못된 번호 인용 | 0 | 0 |

- 지시문을 바꾼 방법은 인용이 올라도 정답 포함이 내려갔지만, 코드로 붙이면 **답 내용은 그대로 두고** 출처만 더하므로 정답 포함이 유지됩니다.
- "인용이 붙은 답"은 이제 모델이 아니라 코드가 붙인 줄도 세므로, 모델의 지시문 준수율을 재는 값이 아닙니다. 출처가 **맞는 쪽을 가리키는지**는 앞 줄의 별도 측정으로 봅니다.
- 한계: 겹침으로 찾는 것이라, 모델이 근거에 없는 내용을 말했을 때 그 말과 가장 겹치는 근거를 붙일 수 있습니다(출처 표시가 내용의 옳음을 보증하지 않습니다).

**잘못된 번호 인용 검사** — 번호를 안 다는 것보다 **틀린 번호를 다는 것**이 더 나쁩니다. 근거가 2개뿐인데 `[자료 5]`라고 쓰는 답을 세는 항목(`bad_cite_answers`)을 평가 도구에 추가했습니다. 모든 조건에서 0이었습니다.

## 문제 9: 질문을 문서로 보낼지 정하기 — 자동 모드의 판단

**배경** — 채팅에는 "문서 검색(RAG)"과 "일반 채팅" 두 모드가 있었고 사용자가 직접 골라야 했습니다. 게다가 부품 핀 질문은 KiCad 라이브러리가 모드와 상관없이 먼저 가로채서, 문서에 대한 질문인데 부품 이름이 들어 있다는 이유로 라이브러리 값이 답으로 나갔습니다(평가 질문 1개가 계속 실패하던 원인). 그래서 질문마다 처리 방식을 **자동으로 판단**하는 모드를 기본값으로 만들었습니다(응답 모드는 4장).

```text
① 올려 둔 문서에 근거가 있으면            → 문서
② 아니고, 라이브러리에 있는 부품 핀 질문이면 → 부품 라이브러리
③ 그 밖은                                  → 일반 대화 (화면에 "문서를 근거로 쓰지 않았습니다" 표시)
```

판단은 **모델이 아니라 규칙**입니다. 빠르고, 같은 질문이면 같은 결과가 나오고, 왜 그렇게 정했는지 설명할 수 있기 때문입니다.

**"문서에 근거가 있다"의 기준** — 벡터 검색은 관련이 없어도 항상 결과를 채워 주므로 점수만으로는 부족합니다. 1위 검색 결과가 (a) 점수가 문턱(0.78) 이상이고 (b) 질문의 낱말이 본문에 1개 이상 실제로 있어야 합니다.

**처음 측정이 낙관적이었다** — 문턱을 정할 때 쓴 질문 38개에서는 틀린 판단이 1개뿐(문서 질문이 일반으로 간 것)이었습니다. 문턱을 정하는 데 쓰지 않은 **새 질문**을 측정 **전에** 써 두고(사전 등록) 같은 문턱으로 쟀습니다.

| 질문 세트 | 질문 수 | 틀린 판단 | 비고 |
|---|---|---|---|
| 문턱을 정할 때 쓴 질문 | 38 | 1 | 같은 자료로 정하고 같은 자료로 잼 → 낙관적 |
| 새 질문 1차 | 21 | 3 (14%) | 일반 질문 2개와 부품 질문 1개가 문서로 감 |
| 새 질문 2차 | 29 | 6 | 부품 질문 7개 중 4개가 문서로 감 |

같은 문턱인데 오류가 더 나온 것입니다. **사전 등록한 대로 문턱을 새 질문 결과로 고치지 않았습니다.** 대신 원인을 봤습니다.

- 부품 질문이 문서로 간 이유: 올려 둔 수업 문서에 `핀`·`정보`·`이름` 같은 흔한 낱말이 많아, 부품 이름이 문서에 하나도 없어도 "낱말이 일치한다"고 판정됐습니다.
- 일반 질문이 문서로 간 이유도 흔한 낱말 하나(`차이`, `코드`)였습니다. 올려 둔 문서 중에는 개발 작업 기록이 있어, 일부는 실제로 근거가 있는 경우일 수 있습니다(표시가 틀렸을 수 있음).

**수정(원리 하나)** — 질문이 라이브러리에 있는 **특정 부품 번호**를 지목하면, 검색된 문서 조각에 **그 부품 번호가 실제로 나올 때만** 문서로 봅니다. 문서가 그 부품을 다룬다는 뜻이 되는 경우만 문서로 보내는 것입니다.

**파일** `routing.py` · 원본 발췌

```python
def has_document_evidence(sources: list[dict], min_score: float, min_terms: int = 1) -> bool:
    """검색 결과 1위가 문서 근거로 볼 만한가."""
    if not sources:
        return False
    top = sources[0]
    if top.get("source") not in (None, "documents"):
        return False                       # 제1장 실습 문장 같은 대체 근거는 '올려 둔 문서'가 아니다
    return (top.get("score") or 0) >= min_score and len(top.get("matched_terms") or []) >= min_terms


def documents_mention(sources: list[dict], tokens: list[str], top: int = 4) -> bool:
    """검색된 문서 조각 중 하나라도 부품 번호를 그대로 담고 있는가 (대소문자 무시)."""
    texts = [str(s.get("text") or "").lower() for s in sources[:top]]
    return any(t.lower() in x for t in tokens for x in texts)
```

**검증** — 수정을 만든 뒤에 쓴 **완전히 새 질문 19개**(3차, 사전 등록)로 다시 쟀습니다.

| 질문 세트 | 질문 수 | 틀린 판단 |
|---|---|---|
| 새 질문 1차 (수정 후) | 21 | 2 (일반 질문 → 문서) |
| 새 질문 2차 (수정 후) | 29 | 2 (일반 질문 → 문서) |
| **새 질문 3차** (수정 뒤에 쓴 질문) | 19 | 1 (일반 질문 → 문서) |

- **부품 질문은 3차에서 7개 모두 정확**했습니다(1·2차는 수정에 쓴 질문이라 증거로 세지 않습니다).
- 남은 오류는 모두 일반 질문이 흔한 낱말 하나 때문에 문서로 가는 경우입니다. 새 질문 세 세트를 합치면 일반 질문 40개 중 5개(12.5%)입니다.

**시도하고 채택하지 않은 개선** — 같은 문제를 더 줄일 수 있는지 두 가지 신호를 재 봤지만, 이 작은 문서 규모(청크 236개)에서는 문서 질문과 일반 질문이 겹쳤습니다.

| 시도 | 결과 |
|---|---|
| 일치한 낱말이 문서에서 얼마나 흔한가 | 일치 낱말에 조사·어미가 붙은 형태(`차이를`, `에서`)가 섞여 깔끔한 기준이 안 됨 |
| 1위 점수가 후보 30개의 중앙값보다 얼마나 튀는가 | 문서 질문 하위 5개(0.025~0.064)와 일반 질문 상위(0.069)가 겹침 |

**후속 질문** — 판단은 마지막 질문 한 줄만 봅니다. 그래서 문서 대화 중에 "그럼 그건 얼마야?" 같은 짧은 후속 질문을 하면 혼자서는 문서와 무관해 보여 일반 대화로 빠졌습니다. 실제 서버에 대화 이력을 붙여 보냈더니 후속 질문 3개 중 2개가 문서를 잃었습니다. 대화 이력을 붙인 평가 세트를 만들어 쟀습니다(검색만 사용). 생성 규칙은 측정 전에 정했습니다: 문서 질문(혼자서도 문서로 판단되는 것) 6개 뒤에 지시어 문장 6개, 일반 질문 6개 뒤에 같은 문장 6개, 문서 질문 뒤에 짧은 새 주제 질문 6개.

| 이력을 쓰는 방식 | 문서 대화 뒤의 후속(36) | 일반 대화 뒤의 후속(36) | 문서 대화 뒤 주제 전환(36) |
|---|---|---|---|
| 쓰지 않음 (기준선) | 12 맞음 | 24 맞음 | 36 맞음 |
| 짧으면 무조건 직전 처리 방식을 이어받음 | 34 맞음 | 36 맞음 | **13 맞음 (23개가 문서에 붙잡힘)** |
| **후속을 가리키는 표현이 있을 때만 이어받음 (채택)** | 29 맞음 | 36 맞음 | 36 맞음 |

무조건 이어받으면 후속 질문은 좋아지지만 주제를 바꾼 짧은 질문의 64%가 문서에 붙잡힙니다. **후속을 가리키는 표현**(그럼·그건·방금·자세히 등, `routing.FOLLOWUP_MARKERS`)이 있을 때만 이어받으면 이 비용이 사라집니다. 이 규칙은 20자 이하의 짧은 질문에만 적용하고(`ROUTE_FOLLOWUP_MAX_CHARS`), 이어받은 경우는 "근거가 약함"으로 표시합니다. 직전이 일반 대화였을 때는 약한 근거만으로는 문서로 가지 않습니다.

위 표의 문장은 표현 목록을 만들 때 본 문장이라 낙관적입니다. 그래서 **목록을 고정한 뒤 새로 쓴 문장**(지시어가 있는 후속 6개, **지시어가 없는 생략형 후속 6개**, 짧은 새 주제 질문 12개)으로 다시 쟀습니다.

| 새 문장(2차) | 기준선 | 채택한 방식 |
|---|---|---|
| 문서 대화 뒤의 후속 질문 72개(생략형 포함) | 12 맞음 | **39 맞음** |
| 문서 대화 뒤의 짧은 새 주제 질문 72개 | 72 맞음 | **72 맞음** |

- 새 주제 질문을 후속으로 잘못 이어받은 경우는 0이었습니다.
- **한계**: "비용은?"·"기간은 얼마야?"처럼 지시어가 없는 생략형 후속 질문은 표현 목록으로 알아볼 수 없어 이어받지 못합니다(72개 중 33개가 여전히 문서를 잃음). 아래에서 이 한계를 줄이는 방법을 따로 시험했습니다.

**지시어 없는 생략형 이어받기** — 가설: 직전 질문에 짧은 말을 덧붙여 다시 검색할 때, 생략형 후속은 점수가 거의 떨어지지 않고 새 주제는 크게 떨어집니다(직전 질문의 내용과 섞이지 않기 때문). 개발용 문장에서 직전 질문 대비 점수 하락을 쟀습니다.

| 하락이 이 값 이하이면 이어받기 | 생략형 후속(36) 이어받음 | 주제 전환(72) 잘못 이어받음 |
|---|---|---|
| 0.02 | 22 (61%) | 1 (1.4%) |
| 0.03 | 29 (81%) | 6 (8%) |
| 0.05 | 35 (97%) | 37 (51%) |

문턱을 **0.02로 고정**하고(`ROUTE_ELLIPSIS_MAX_DROP`), 문턱을 정할 때 쓰지 않은 **새 문장 30개와 새 직전 질문 6개**로 사전 등록해 검증했습니다.

| 새 문장 | 지시어 규칙만 | + 생략형 이어받기 |
|---|---|---|
| 문서 대화 뒤 후속 질문 72개 | 30 맞음 | **55 맞음 (+25)** |
| 문서 대화 뒤 짧은 새 주제 108개 | 96 맞음 (틀림 12) | 81 맞음 (**틀림 27, +15**) |

개발용 문장에서 본 주제 전환 오류(1.4%)는 낙관적이었습니다. 새 문장에서는 오류가 12개에서 27개로 늘었습니다. 그래도 후속 질문이 +25, 오류가 +15라서 순이득이 있다고 보고 **채택**했습니다. 문서 중심의 대화에서는 생략형 후속이 흔하고, 잘못 이어받은 경우에는 "근거가 약함" 안내가 나오기 때문입니다. `.env`에 `ROUTE_ELLIPSIS_MAX_DROP=0`을 넣으면 끕니다.
- 명시적인 `문서만` 모드의 검색은 이번에 바꾸지 않았습니다(마지막 질문만 검색).

**불확실한 구간은 숨기지 않는다** — 점수가 문턱을 막 넘은 구간(0.78~0.85)이거나 일치한 낱말이 1개뿐이면 `route_strength`를 `weak`로 돌려주고, 화면에 "문서와의 관련이 약합니다. 문서와 무관한 질문이면 응답 모드를 '일반만'으로 바꿔 보세요"라고 알려 줍니다. 측정(표본 안): 문서로 간 질문 중 정말 문서 질문 21개 중 7개(33%)가 `weak`였고, 오판 3개는 모두 `weak`였습니다. 이 3개를 본 뒤 만든 장치라 새 질문으로 다시 확인해야 합니다(**미검증**).

```bash
# 판단 정확도 확인: 검색만 쓰고 답은 만들지 않음. 질문 번호만 출력
.venv/bin/python scripts/run-route-eval.py
```

> 이 절의 질문 세트는 모두 내 PC의 `data/eval/`에만 있고 GitHub에 올라가지 않습니다. **정답 표시(문서·부품·일반)는 Claude가 붙인 초안**이라 사람이 검토하기 전입니다. 실제로 한 질문은 내가 "일반"이라 표시했는데 올려 둔 문서에 관련 내용이 있어 표시가 틀렸고 교체했습니다.

| 파일 이름 + 문서 첫머리를 붙이기 | 설정을 정한 문서: 정답 쪽 1위 0.818 → 0.727 | 모든 지표가 같거나 나빠졌습니다. |
| 벡터 순위와 키워드 순위 합치기 (RRF) | 수치가 비정상 | 실험 코드가 문서가 다른 청크를 같은 것으로 합쳤습니다. 결과를 무효로 처리했습니다. |
| 모델이 다시 쓴 답 전체를 조건부로 채택 | 지시문 두 가지 중 하나에서 21개 중 1개가 핵심 낱말을 잃음 | 모델이 외국 문자와 상관없는 용어까지 바꿉니다. 자리별 수정만 옮기는 방식으로 바꿨습니다. |

| 한자 표에 "표준 음 표시가 하나면 고른다" 기준 | `樂器`가 `낙기`로 바뀜 | 음이 여럿인 글자는 표에서 뺐습니다(176자). |
| 모든 답에 한자 음 표 적용 | 거의 중국어인 답이 한글·한자 뒤섞인 글이 됨 | 한글이 외국 문자의 2배 이상인 답에만 씁니다. |
| 출처 지시문 "각 문장 끝에 번호를 반드시" | 인용 0.386 → 0.933, 정답 포함 0.932 → 0.822 | 정답 포함이 범위가 겹치지 않게 내려갔습니다(답이 짧아짐). |

| 일치한 낱말의 문서 내 흔함으로 판단 | 기준이 안 됨 | 일치 낱말에 조사·어미가 붙은 형태가 섞입니다. |
| 1위 점수가 후보의 중앙값보다 튀는 정도로 판단 | 문서·일반 질문이 겹침 | 문서 질문 하위 5개와 일반 질문 상위가 같은 범위입니다. |

파일 이름을 붙이는 실험은 문서 16개(1,190청크)를 모두 지금 규칙으로 다시 나눈 상태를 가정하고 메모리 안에서 쟀습니다. 문서를 찾는 능력은 좋아지지만 쪽을 가려내는 능력이 떨어지는, 서로 반대 방향의 효과입니다.

**남은 한계**

- 평가 질문은 사람이 만든 것이 아닙니다. 특히 최종 확인 질문은 고유한 용어가 많아 쉬운 편일 수 있습니다.
- 정답이 2위인데 컷오프에 잘리는 질문과, 질문이 막연해 정답을 찾지 못하는 질문이 각각 하나씩 남아 있습니다.
- 같은 문서 안에 비슷한 쪽이 많은 슬라이드 자료에서는 정답 쪽이 2위로 밀리는 일이 잦습니다(hit@1 0.750).
- 검색 단위는 여전히 쪽 단위(최대 1,150자)입니다. 화면에는 발췌를 보여 주지만 검색되는 조각 자체가 큽니다.
- 답변 확인은 핵심 낱말이 있는지만 봅니다. 근거 대조(문제 7)가 문서에 없는 숫자·영문을 후보로 알려 주지만, 계산한 값도 걸리고 근거에 있는 숫자를 엉뚱하게 쓴 답은 못 거릅니다.
- 한자 음 표에 없는 글자(음이 여러 개인 176자 등)와 접두어 뒤의 두음법칙 같은 예외는 고치지 못합니다. 표에 없는 글자가 2자 이상 남으면 모델이 다시 쓰고, 그래도 안 되면 한국어 위주의 답은 원래 답을 그대로 보여 줍니다.
- 출처 표시는 이제 코드가 붙입니다(인용 0.39 → 0.98). 다만 겹침으로 고르는 것이라 내용의 옳음을 보증하지 않습니다. 지시문을 바꾸는 방법은 정답 포함이 내려가서 쓰지 않았습니다.
- 자동 모드의 생략형 후속 이어받기는 짧은 새 주제를 문서에 붙잡는 오류가 늘어납니다(108개 중 12 → 27). 오류가 나면 "근거가 약함" 안내를 보고 `일반만`으로 바꿉니다.
- 자동 모드는 올려 둔 문서에 흔한 낱말이 있는 일반 질문을 문서로 보내는 일이 있습니다(새 질문 일반 40개 중 5개). 흔한 낱말 하나로는 판단 신호가 약합니다. 질문 세트의 정답 표시는 사람이 검토하기 전입니다.
- 재순위 모델(reranker)이나 LlamaIndex 같은 프레임워크는 도입하지 않았습니다. LlamaIndex의 Elasticsearch 연동 패키지는 최신판(0.7.0)까지 `elasticsearch<9`를 요구해, 이 프로젝트의 Elasticsearch 9 클라이언트와 함께 설치할 수 없다는 것만 확인했습니다(2026-11-12, 설치하지 않고 의존성만 계산). 효과는 재지 않았습니다.

## 핵심 정리

- 연결이 정상이어도 검색 품질은 따로 재야 합니다. 질문·정답·근거 쪽으로 평가 세트를 만들고 채점 도구로 숫자를 봅니다.
- 벡터 검색은 관련이 없어도 요청한 개수를 채웁니다. 1위와 점수 차이가 큰 결과는 숨깁니다.
- 짧은 검색어에서는 벡터 유사도만으로 부족합니다. 검색어가 본문에 실제로 있는지를 점수에 더하고, 그런 청크를 후보에도 넣습니다.
- 설정은 그 설정을 정할 때 본 문서가 아닌, 처음 보는 문서로 다시 검증합니다. 고치는 데 쓴 문서와 최종 확인용 문서를 나눕니다.
- 검색이 맞아도 답변은 따로 확인합니다. 기계적 확인은 핵심 낱말까지만 보므로, 저장된 답을 직접 읽는 일을 빼먹지 않습니다.
- 모델에게 글을 고치게 할 때는 고친 글 전체를 받지 않습니다. 원래 글과 비교해 고치려던 자리의 변경만 옮기면, 나머지는 바뀔 수 없습니다.
- 같은 질문도 답이 실행마다 다릅니다. 변경 효과는 여러 번 재서 전후의 범위가 겹치는지로 판단합니다.
- 모델에게 맡기지 않아도 되는 교정은 규칙과 표로 합니다. 다만 음이 여러 개인 글자처럼 확신할 수 없는 것은 바꾸지 않고 남깁니다.
- 숫자와 영문이 근거에 있는지 대조하면 사람이 읽을 후보를 줄일 수 있습니다. 판정이 아니라 후보 목록입니다.
- 지시문을 바꿔 한 지표를 올리면 다른 지표가 내려갈 수 있습니다. 올리려던 지표만 보지 말고 같이 재서 판단합니다.
- 판단 규칙은 정할 때 쓴 질문이 아니라, 정한 뒤에 사전 등록한 새 질문으로 검증합니다. 처음 수치는 낙관적이었습니다.
- 효과가 없던 실험과 잘못된 실험도 기록합니다. 다음에 같은 길을 다시 가지 않기 위해서입니다.
